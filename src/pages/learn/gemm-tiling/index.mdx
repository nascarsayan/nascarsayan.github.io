Most of an LLM's FLOPs are in **GEMMs** (general matrix-matrix multiplies): the Q/K/V and output projections, and the MLP or expert layers. A GEMM computes $$C = A \cdot B$$, with $$A$$ of size $$M \times K$$, $$B$$ of size $$K \times N$$ and $$C$$ of size $$M \times N$$. In a transformer layer, $$M$$ is the number of tokens, $$K$$ the input width and $$N$$ the output width. This page explains how a GPU kernel turns that into work the matrix cores can do at full speed.

## The idea first

**Every output needs a whole row and a whole column.** One number of C, `C[i][j]`, is a dot product: row $$i$$ of A times column $$j$$ of B. Neighbouring outputs share inputs: everything in row $$i$$ of C uses the same row of A, everything in column *j* uses the same column of B. Tiling is just **noticing that sharing and fetching each shared piece once**.

**Sandwich analogy.** A team must make 16 sandwiches: every combination of 4 breads (rows of A) and 4 fillings (columns of B). One cook per sandwich, each walking to the pantry for their own bread and filling, makes 32 trips. A team that puts the 4 breads and 4 fillings on its table once makes 8 trips, and makes all 16 sandwiches from the table. Bigger teams save more: a 256 × 256 tile fetches 512 items for 65,536 outputs.

| Piece | Sandwich version | The question it answers |
| --- | --- | --- |
| Workgroup tile | one team and its 16 sandwiches | "Which block of C does this team own?" |
| LDS (shared memory) | the team table | "What did we fetch once, for all of us?" |
| K-step | the sandwich has many layers; bring one layer's worth at a time | "How much of the row and column fits on the table at once?" |
| Wave tile, registers | each cook's hands: their share of sandwiches, kept while layers are added | "Where do partial results live until done?" |
| MFMA / Tensor Core | a machine that assembles a 32 × 32 block of sandwiches in one go | "What is the smallest unit of work the hardware does?" |
| Epilogue | wrap and ship each finished sandwich once | "What cheap step can we do before the result leaves?" |

**Where the analogy breaks.** A real row of A is thousands of numbers long (K), and the table is small (160 KB of LDS on MI355X), so the team brings it in K-steps and keeps adding into the same results. Partial results live in registers, not on the table. And teams do not choose their sandwiches: the kernel assigns tiles, and neighbouring teams that share rows can still share them through the L2 cache.

## The naive kernel is memory-bound

Give each thread one element of C. It reads a row of A and a column of B (2K values) and does K multiply-adds (2K FLOPs). In BF16 that is 2K FLOPs for 4K bytes: **0.5 FLOP/B**. The MI355X BF16 ridge point is about 310 FLOP/B ([roofline](/learn/gpu-memory-hierarchy/#the-roofline)). The naive kernel would run at well under 1 % of peak, even though the whole matrix multiply has plenty of reuse: every element of A is needed by all N columns of C.

The fix is **tiling**: load a block of A and a block of B once into fast memory, and compute every output that needs them before loading the next block.

## The tiling hierarchy

<Diagram spec={tiles} title="Tiles at each level (example sizes for MI355X)" caption="Tile sizes are an illustrative configuration, not the ones a specific library picks. Hover for the arithmetic." />

| Level | Lives in | Example size | What it buys |
| --- | --- | --- | --- |
| Workgroup tile | LDS (shared memory) | 256 × 256 outputs, K-step 64 | reuse of A and B slices across a whole tile |
| Wave tile | registers (AGPRs for C, VGPRs for A/B fragments) | 128 × 128 per wavefront | reuse of fragments across many MFMAs |
| Instruction tile | the matrix core | `v_mfma_f32_32x32x16_bf16`: 32 × 32 outputs, $$K = 16$$ | one instruction = 32,768 FLOPs |

### Intensity of a tile

A workgroup tile of $$M_t \times N_t$$ outputs, for each K-step of depth $$k_t$$, loads $$(M_t + N_t)\,k_t$$ elements and does $$2\,M_t N_t k_t$$ FLOPs. With $$b$$ bytes per element:

$$
I = \frac{2\,M_t N_t k_t}{(M_t + N_t)\,k_t\,b} = \frac{2\,M_t N_t}{(M_t + N_t)\,b}
$$

| Tile (BF16, $$b = 2$$) | FLOP per byte loaded |
| --- | --- |
| 1 × 1 (naive) | 0.5 |
| 64 × 64 | 32 |
| 128 × 128 | 64 |
| 256 × 256 | 128 |

That is intensity per tile *as seen by L2*. Neighbouring workgroups load the same A rows and B columns, so L2 and the Infinity Cache serve many of those loads and HBM sees fewer. Libraries order workgroups (Triton's `GROUP_SIZE_M` "grouped ordering", AMD's XCD-aware remapping) so tiles that share data run at the same time on the same L2. Bigger tiles mean higher intensity, but need more LDS and registers, and give fewer workgroups.

### Budget check on MI355X

Take the 256 × 256 tile with a K-step of 64 in BF16:

| Item | Size | Fits? |
| --- | --- | --- |
| A slice 256 × 64 + B slice 64 × 256 | 64 KB of LDS | yes |
| Double-buffered (load next while computing current) | 128 KB | yes on MI355X (160 KB) and H100 (228 KB); **no** on MI300X (64 KB) |
| C accumulators, 256 × 256 FP32 | 256 KB, split over 4 waves = 256 AGPRs per lane | uses the whole AGPR bank |
| Waves per SIMD | 256 AGPRs + up to 256 VGPRs = 512 | **1** (12.5 % occupancy) |

That is normal. A good GEMM keeps the matrix cores busy with one or two waves per SIMD, because each wave already has many independent MFMAs and loads in flight. → [Occupancy](/learn/gpu-execution-model/#occupancy-how-many-waves-fit)

## Inside the K loop

Each workgroup walks along K. A straightforward version, per K-step:

1. Every lane issues `global_load_dwordx4` for its share of the next A and B slices.
2. Wait (`s_waitcnt vmcnt`), then write them to LDS with `ds_write_b128`.
3. Barrier (`s_barrier`) so every wave sees the full slices.
4. Each wave reads its fragments with `ds_read_b128` and issues its MFMAs.
5. Barrier, then the next K-step.

The real gfx950 loop on [PTX and AMDGCN](/learn/gpu-isa-ptx/#feeding-the-matrix-cores-amd) is exactly this, for a single wave.

### Double buffering (software pipelining)

The straightforward loop leaves the matrix cores idle during steps 1–3. Production kernels keep **two** LDS buffers. While MFMAs run on buffer 0, the loads for step *k + 1* fill buffer 1; then they swap.

 On NVIDIA the hardware helps: `cp.async` (Ampere) and TMA (Hopper, `cp.async.bulk.tensor`) copy global → shared memory asynchronously, and Hopper's `wgmma` and Blackwell's `tcgen05.mma` are themselves asynchronous. On gfx950, `global_load_lds_dwordx4` loads straight into LDS without passing through VGPRs. Kernels with more LDS to spare use three or four stages instead of two.

### The epilogue

When the K loop ends, the accumulators hold FP32 results. The **epilogue** converts them (to BF16 or FP8), applies anything cheap and element-wise (bias, activation such as SiLU, a residual add, an output scale), and stores the tile. Fusing those steps here saves a full extra read and write of C through HBM, which for element-wise work is the entire cost (it is memory-bound at ~0.2 FLOP/B).

### What it looks like in Triton (illustrative)

Simplified from the official Triton matrix-multiplication tutorial. Triton lets the author write the workgroup tile; the compiler produces the LDS staging, MFMA/MMA instructions and pipelining:

```python
# Illustrative: one program (= one workgroup) computes one BLOCK_M x BLOCK_N tile of C.
acc = tl.zeros((BLOCK_M, BLOCK_N), dtype=tl.float32)
for k in range(0, tl.cdiv(K, BLOCK_K)):
    a = tl.load(a_ptrs, mask=offs_k[None, :] < K - k * BLOCK_K, other=0.0)   # A slice
    b = tl.load(b_ptrs, mask=offs_k[:, None] < K - k * BLOCK_K, other=0.0)   # B slice
    acc = tl.dot(a, b, acc)                      # becomes v_mfma_* / mma / wgmma
    a_ptrs += BLOCK_K * stride_ak
    b_ptrs += BLOCK_K * stride_bk
c = acc.to(tl.bfloat16)                          # epilogue: convert (and fuse activations here)
tl.store(c_ptrs, c, mask=c_mask)
```

## When there are not enough tiles

Tiling assumes M and N are large. In decode they are not: M is the number of sequences in the batch.

**Worked example: gpt-oss-120b Q/K/V projection.** Hidden size $$K = 2{,}880$$. Output $$N = (64\ \text{query} + 8\ \text{key} + 8\ \text{value heads}) \times 64 = 5{,}120$$ (published config). On an MI355X with 256 CUs:

| Case | M | Tile | Workgroups | CUs used |
| --- | --- | --- | --- | --- |
| Prefill, 4,000 tokens | 4,000 | 256 × 256 | 16 × 20 = 320 | all 256 (1.25 waves of tiles) |
| Decode, batch 64 | 64 | 256 × 256 | 1 × 20 = 20 | **20 of 256 (8 %)** |
| Decode, batch 64 | 64 | 64 × 128 | 1 × 40 = 40 | 40 of 256 |
| Decode, batch 64, split-K by 4 | 64 | 64 × 128 | 160 | 160 of 256 |

Fixes for skinny shapes:

- **Smaller tiles.** Fewer FLOPs per byte, but decode is memory-bound anyway.
- **Split-K.** Several workgroups each take part of K for the same output tile, then their partial sums are added (atomics or a second small kernel).
- **Stream-K.** Divide the total K-iterations evenly across exactly one wave of workgroups, so no CU sits idle at the end.
- **GEMV kernels.** For batch 1–8, a matrix-vector kernel that just streams weights at full bandwidth is often fastest.

Libraries choose among these per shape. hipBLASLt (AMD) and cuBLASLt (NVIDIA) keep tuned tables per GPU model, which is one reason the same model can need re-tuning on a new GPU.

## Grouped GEMM for mixture-of-experts

An MoE layer has many expert weight matrices (gpt-oss-120b: 128 experts per layer, 4 chosen per token). Each expert multiplies only the tokens routed to it: many small GEMMs of different sizes. Launching 128 kernels would waste most of the GPU, so servers run **one grouped GEMM**. vLLM's `fused_moe` Triton kernel shows the pattern:

1. **Route.** A small kernel picks the top-4 experts per token.
2. **Align.** `moe_align_block_size` sorts the (token, expert) pairs by expert and pads each expert's list to a multiple of `BLOCK_SIZE_M`. It outputs `sorted_token_ids` and `expert_ids` (one expert per M-block).
3. **Grouped GEMM.** Each workgroup reads `expert_ids[pid_m]` to pick which expert's B matrix to use, gathers its tokens' rows of A via `sorted_token_ids`, and runs the normal tiled loop.
4. **Combine.** Results are weighted by the router scores and summed per token.

The padding is the cost. In decode, an expert typically has 1–3 tokens; padding to `BLOCK_SIZE_M` = 16 or 64 means most of the tile computes zeros, and each expert's weights are read for very few tokens. → [Roofline for MoE](/learn/gpu-memory-hierarchy/#apply-it-to-an-llm)

On AMD, the AITER library provides MoE and GEMM kernels tuned for MI300/MI355 that vLLM can use instead of the Triton path.

<Callout tone="note" title="Misconception: one GEMM kernel">
A single `torch.matmul` call can dispatch to dozens of different kernels depending on M, N, K, data type and GPU. Profiles therefore show long, mangled kernel names (tile sizes and pipeline depth are often encoded in them). Two GPUs running "the same model" usually run different GEMM kernels.
</Callout>

## How this shows up in operations

- **Performance after a ROCm or driver upgrade can move.** GEMM libraries and their tuning tables ship with ROCm. A new version may pick different kernels for the same shapes.
- **Batch size is a GPU efficiency knob.** Small decode batches leave most CUs idle in GEMMs, which shows up as low throughput with "busy" utilization counters.
- **Kernel names in traces identify the library.** Names starting with `Cijk_` come from Tensile (rocBLAS/hipBLASLt); `fused_moe_kernel` is vLLM's Triton MoE kernel. → [LLM kernels](/learn/llm-kernels/#seeing-real-kernels)
