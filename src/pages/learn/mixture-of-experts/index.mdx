In every transformer layer, after attention, each token goes through an MLP (see [Tokens and transformers](/learn/tokens-and-transformers/)). In a **dense** model that MLP is one big block that every token uses. In a **mixture-of-experts (MoE)** model it is many smaller blocks, the **experts**, and each token uses only a few. gpt-oss-120b, the running example on these pages, is an MoE model.

## The idea

Picture a clinic with 128 specialists and a receptionist. Each patient (a token) is sent to the 4 specialists the receptionist thinks fit best, and the patient's notes are a blend of their 4 reports, weighted by how confident the receptionist was. The clinic can employ a huge staff (lots of knowledge stored) while each patient costs only 4 consultations (little compute).

- The **router** is the receptionist: it answers "which experts suit this token?"
- The **top-4** cut answers "how many do we pay for?" The other 124 do no work for this token.
- The **weights** answer "how much does each opinion count?"
- The **weighted sum** is the blended report, added to the token's vector.

Where the analogy breaks: experts are not topic specialists (no "code expert" or "French expert"); routing is learned per token and per layer, so the same word visits a different 4 in each of the 36 layers. And all 128 specialists must be on site at all times, because any token may need any of them: MoE saves compute, not memory.

## Training keeps the load spread

If the router sent most tokens to a few favourite experts, those would become a bottleneck and the rest would waste memory. Training adds an auxiliary **load-balancing loss** that penalises uneven use (gpt-oss's config lists `router_aux_loss_coef: 0.9`). In inference nothing forces balance; the router does what it learned.

## Total versus active parameters

| | Total | Per token ("active") |
| --- | --- | --- |
| Experts | 128 × 36 × 24.9 M ≈ 114.7 B | 4 × 36 × 24.9 M ≈ 3.6 B |
| Attention, router, norms | ≈ 0.97 B | all of it |
| Embedding + unembedding | 1.16 B | the unembedding (0.58 B) |
| **Model** | **116.8 B** | **5.1 B** |

Two different costs follow:

- **Compute per token tracks active parameters.** About 2 FLOPs per active weight, so roughly 9 GFLOP per token (excluding the unembedding). A dense 117 B model would need about 230 GFLOP.
- **Memory tracks total parameters.** All 128 experts must be loaded, because any token may pick any expert. That is why gpt-oss-120b quantizes the experts to MXFP4 (4.25 bits per weight on average): the experts shrink to about 61 GB and the whole checkpoint to 60.8 GiB, so it fits one 80 GB GPU, and leaves an MI355X (288 GB) with over 200 GB for the [KV cache](/learn/attention-and-kv-cache/).

**MXFP4** is a "microscaling" 4-bit floating-point format: each weight is a 4-bit float, and each block of 32 weights shares one 8-bit scale. That is where 4.25 bits per weight comes from (4 + 8/32). MI355X has matrix instructions for MXFP4 and MXFP6 ([spec sheet](https://www.amd.com/en/products/accelerators/instinct/mi350/mi355x.html): about 10 PFLOP/s peak). Whether a given server's kernels run the matrix math in 4-bit or upconvert to 8-bit depends on the kernel library.

## What routing does to batching

One expert's weights are read from memory once per layer per step, then used for **every token routed to it in that step**. So the useful question is: how many tokens does each expert get?

Two lessons:

1. **Decode batching helps MoE less than dense models.** Going from 1 to 64 users multiplies the expert bytes read per step by about 27–28× (simulation above, formula in the calculator), because new users wake new experts. Each expert still sees only 2–3 tokens, so arithmetic intensity barely rises. See [Decode](/learn/decode-phase/) and [Batching and scheduling](/learn/batching-and-scheduling/).
2. **Prefill needs big steps to be compute-bound.** An expert does 2 FLOPs per weight per token and costs 0.53 bytes per weight, so its intensity is about 3.8 × tokens per expert. MI355X's ridge point is about 5 PFLOP/s ÷ 8 TB/s ≈ 625 FLOP/byte (spec sheet, approximate; see [roofline](/learn/gpu-memory-hierarchy/)). An expert becomes compute-bound at about 165 tokens, which needs a step of about 165 × 128 / 4 ≈ **5,300 tokens**.

### What it means for short prompts

Short prompts pay a near-fixed cost: every step must read all the experts at least once (about 61 GB at 8 TB/s is 7.6 ms at full bandwidth), plus fixed per-request overhead. Throughput in tokens per second only climbs to its plateau once a step holds several thousand tokens.

## Splitting experts across GPUs

When a model does not fit one GPU, or to raise throughput, servers use **expert parallelism (EP)**: different GPUs hold different experts. Each MoE layer then needs two all-to-all exchanges: send each token's hidden state to the GPUs owning its chosen experts, then gather the results. That traffic runs over the GPU-to-GPU links (XGMI on AMD, NVLink on NVIDIA; see [GPU memory and interconnects](/learn/gpu-memory-and-interconnects/)), and uneven routing makes the busiest GPU set the pace.

gpt-oss-120b fits on **one whole MI355X** (the ~65 GB checkpoint in 288 GB), so a replica can run without tensor or expert parallelism. Larger MoE models, or NVL72-style racks, are where EP matters.

## On the GPU

A naive implementation would loop over experts. Real servers sort tokens by expert and run one **grouped GEMM** (many small matrix multiplies in one kernel launch), often fused with the routing and the weighted sum (vLLM calls it fused MoE). The kernel view is on [Prefill and decode as kernels](/learn/llm-kernels/).

<Callout tone="note" title="How this shows up on dashboards">
MoE explains two things you may see on GPU dashboards: prefill GPUs with full HBM (weights ~65 GB plus a large KV reservation) but modest compute use at low traffic, and per-request latency that hardly changes between a 50-token and a 500-token prompt. Neither is a fault.
</Callout>

## Common misconceptions

- **"Experts are topic specialists (one for code, one for French)."** Routing is per token per layer and is learned for loss, not for human topics. Experts do not map cleanly to subjects.
- **"Only 5 B parameters, so it needs 5 B parameters of memory."** It needs all 117 B loaded; only compute shrinks.
- **"MoE makes decode cheap."** Per user, yes: 1.9 GB of expert bytes instead of 61 GB. At a batch of 64, the step reads most of the model anyway.
