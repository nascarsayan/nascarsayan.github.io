This page is the toolbox for AMD GPU nodes. Every command runs **on the GPU node** (reach it with `ssh` from the management node). The output is illustrative: made-up but realistic values for one example 8× MI355X node called `gpu-node-1`, trimmed to the lines that matter.

## The idea

A GPU node is like a server with eight very expensive, very hot disks in it. You want to know the same things you would ask about disks: *which one is this, what model is it, how is it doing right now, who is using it, is it damaged, are its cables up?* `amd-smi` is one tool that answers all six, the way `lsblk`, `smartctl`, `iostat`, `lsof` and `ethtool` do between them for storage and network.

| Question | amd-smi subcommand | The disk-world equivalent |
| --- | --- | --- |
| Which card is this? | `list -e` | `ls -l /dev/disk/by-path` |
| What is it, and what are its limits? | `static` | the spec sheet, `smartctl -i` |
| How is it doing now? | `metric`, `monitor` | `iostat`, `sensors` |
| Who is using it? | `process` | `lsof /dev/sdX` |
| Is it damaged? | `bad-pages`, `ras` | SMART reallocated sectors |
| Are its links up? | `xgmi`, `topology` | `ethtool`, `ip link` |

Where the analogy breaks: disks fail one at a time, and you can reset one without touching the others. The eight GPUs in an MI355X node are wired into one shared fabric, called a **hive**. Resetting one resets all eight. That is why everything below starts read-only.

Under every tool sits one fact: **only the `amdgpu` kernel driver talks to the chip.** Every tool is a reader of what the driver exposes. Step through the diagram to see which path each tool takes.

<Diagram spec={stack} title="Every AMD tool reads through the driver">
  <Step title="amd-smi" path="cli -> lib -> sysfs -> drv -> gpu">`amd-smi metric` calls the AMD SMI library, which reads sysfs files that the driver fills by asking the GPU's firmware.</Step>
  <Step title="The metrics exporter" path="exp -> lib -> sysfs -> drv -> gpu">The exporter Pod uses the same library, on every Prometheus scrape (every 30 s). Same data, same path: if amd-smi is wrong, the metrics are wrong too.</Step>
  <Step title="rocminfo" path="rinfo -> kfd -> drv -> gpu">rocminfo asks the ROCm runtime through `/dev/kfd`, the interface programs use to run work on the GPU. A GPU that amd-smi lists but rocminfo misses is visible to the driver and unusable by programs.</Step>
  <Step title="The kernel log" focus="drv, drv -> klog, klog, jctl, jctl -> klog">The driver also writes events (errors, resets, hangs) to the kernel log. `journalctl -k` reads only the host's log, so it still works when the GPU does not answer.</Step>
  <Step title="A wedged GPU" path="cli -> lib -> sysfs -> drv -> gpu:hang" state={{ gpu: { tone: 'risk', detail: 'firmware not answering' } }}>When the GPU's firmware stops answering, amd-smi blocks. Run it under `timeout 30`, and read `journalctl -k` first.</Step>

## Worked example: reading one GPU, field by field

Follow GPU 4 on `gpu-node-1`, which a prefill engine is using. Each step is one command, example output trimmed, with the lines to read highlighted and explained. Common flags on every subcommand: `-g <index|BDF|UUID|all>` picks GPUs, `--json` or `--csv` gives machine-readable output, `-h` lists the subcommand's flags.

## Other subcommands

`amd-smi --help` on 26.0.0 lists: `version`, `list`, `static`, `firmware`, `bad-pages`, `metric`, `process`, `event`, `topology`, `set`, `reset`, `monitor`, `xgmi`, `partition`, `ras`, `node`, `fabric`. Beyond the walkthrough:

| Subcommand | What it shows (example) | Read it for |
| --- | --- | --- |
| `firmware` | per-GPU firmware list, e.g. `PSP_SOSDRV 00.00.00.10`, `PM 00.01.02.03`, `PLDM_BUNDLE 01.00.00.00` | version drift across the 8 GPUs and across nodes after a repair |
| `topology -t` / `-o` / `-b` | `XGMI` between every pair, 1 hop, NUMA bandwidth 50000-50000 | all 8 GPUs connect directly: one hive |
| `xgmi` (no flags) | bit rate 32 Gb/s, max bandwidth 512 Gb/s per link, read/write counters | a slow or erroring link; `metric -x` for errors |
| `partition` | `NPS1`, `SPX`, memory caps `NPS1,NPS2` | partition mode; other profiles (`DPX`, `QPX`, `CPX`) split a GPU into 2, 4 or 8 |
| `ras --cper`, `ras --afid --cper-file <f>` | error records and AMD Field IDs (needs `sudo`) | evidence for AMD support; `--cper --folder` **writes files** |
| `node` | baseboard (UBB) temperatures, retimer regulators, node power threshold 12000 W, node power management disabled | the board around the GPUs |

Two firmware pieces matter most when things break. The **PSP** (Platform Security Processor) boots the chip and loads every other firmware. The **SMU**, shown as `PM`, manages power and clocks and executes resets. `amd-smi firmware` only reads; flashing goes through the BMC (Redfish) during provisioning or maintenance. Details of `ras` and the missing records for fatal ATHUB events are in [AMD RAS and ECC](/learn/amd-ras-and-ecc/).

## rocm-smi and rocminfo

`rocm-smi` is the older tool, kept for scripts. With no flags it gives a compact table:

```text
$ rocm-smi                     # example output, trimmed
Device  Node  IDs              Temp        Power     Partitions          SCLK     MCLK     Fan  Perf  PwrCap   VRAM%  GPU%
              (DID,     GUID)  (Junction)  (Socket)  (Mem, Compute, ID)
0       2     0x75a3,   12345  45.0°C      250.0W    NPS1, SPX, 0        100Mhz   2000Mhz  0%   auto  1400.0W  0%     0%
4       6     0x75a3,   45678  50.0°C      320.0W    NPS1, SPX, 0        2400Mhz  2000Mhz  0%   auto  1400.0W  87%    0%
```

`rocminfo` lists **agents**: each CPU NUMA node first (two on the example node), then each GPU. A GPU in `amd-smi list` but missing from `rocminfo` points at the runtime layer (KFD, `/dev/kfd` permissions, a wedged device), not at the PCI link.

## sysfs: the files under the tools

The full set used in this track (example values for GPU 4):

| File (under `/sys/class/drm/card5/device/`) | Example value | Meaning |
| --- | --- | --- |
| `current_compute_partition`, `current_memory_partition` | `SPX`, `NPS1` | partition mode |
| `mem_info_vram_total`, `mem_info_vram_used` | `309237645312`, `268435456000` (bytes) | HBM size and use |
| `gpu_busy_percent` | `0` | engine busy, % |
| `serial_number`, `product_name` | `SN-EXAMPLE-0005`, `AMD Instinct MI355X OAM` | board identity |
| `current_link_speed`, `current_link_width` | `32.0 GT/s PCIe`, `16` | PCIe link; fewer lanes or lower speed is a degraded link |
| `ras/features` | `feature mask: 0xfffff` | which RAS blocks are on |
| `ras/aca_umc` (also `aca_gfx`, `aca_xgmi_wafl`, …) | `ue: 0 ce: 0 de: 0` | per-block error counts on this driver |
| `ras/event_state` | `Fatal Error: count:0` | fatal and poison events since boot |
| `ras/gpu_vram_bad_pages` | empty | bad pages, `pfn : size : R/P/F` |
| `xgmi_hive_info/xgmi_hive_id` | (number) | GPUs with the same id share a hive |
| `xgmi_physical_id` | `6` | position in the hive |
| `hwmon/hwmon*/temp2_input`, `temp3_input` | `50000`, `38000` | junction, memory, in millidegrees |
| `hwmon/hwmon*/power1_input` | `320000000` | socket power, µW |
| `aer_dev_correctable`, `aer_dev_nonfatal`, `aer_dev_fatal` | all `0` | PCIe Advanced Error Reporting counters |

The kernel documentation names the per-block files `<block>_err_count`. On recent amdgpu drivers (6.14.0 in this example) they do not exist; the counts are in `ras/aca_<block>` instead. Scripts that hard-code the old names silently read nothing.

## The kernel log

`journalctl -k` is the most reliable record of a GPU fault. After a couple of weeks of uptime, `dmesg` can return no `amdgpu` lines at all (the ring buffer has wrapped), while `journalctl -k` still has the boot messages. Use journald.

```shell
journalctl -k --since -1d | grep -iE 'amdgpu.*(ras|reset|hang|timeout|fault|poison|fatal)'
```

A healthy boot shows one RAS line per GPU:

```text
amdgpu 0000:e5:00.0: RAS INFO: ras initialized successfully, hardware ability[fffff] ras_mask[fffff]
amdgpu 0000:e5:00.0: AMDGPU RAS Is Ready.
```

Patterns that mean trouble:

| Pattern | Meaning |
| --- | --- |
| `RAS Intr triggered` / `ERREVENT_ATHUB_INTERRUPT` | a fatal hardware event; on a failing GPU it can repeat thousands of times |
| `GPU reset begin` | the driver started a reset; printed once |
| `ring … timeout` | a queue stopped making progress: a hang |
| `GPU reset succeeded, trying to resume` | only means the reinit path ran; **not** proof of recovery |
| `PSP resume failed` / `-62` | the GPU's boot processor did not come back; needs a cold power cycle |
| `bad page` / `poison` | memory errors being contained |
| `AER:` | PCIe errors on the link |


## Validation and diagnostics (disruptive, described only)

These tools load the GPUs to the limit or push traffic between them. They need the node **cordoned and drained**, and the workload owner must confirm the GPUs are free first. They were not run for this page.

| Tool | What it does | Runtime | Notes |
| --- | --- | --- | --- |
| **RVS** (ROCm Validation Suite, `rvs`) | modules that stress compute, memory, PCIe and peer links, and check results against limits | minutes per module | public docs; config files choose the tests |
| **AGFHC** (AMD GPU Field Health Check, `/opt/amd/agfhc/agfhc`) | AMD's field diagnostic, run before an RMA and for burn-in; adds multi-GPU XGMI tests | `single_pass` about 6 min; a burn-in recipe about 6 h | distributed by AMD; no public docs found. Recipes include `hbm_lvl5`, `pcie_lvl2`, `all_lvl5` |
| **TransferBench** | measures copy bandwidth between GPUs and host | minutes | finds a slow XGMI link or PCIe path |


Two limits to remember:

- A clean AGFHC pass does not prove a part is healthy. An intermittent fault that comes every 3 days on average is caught by a 2-hour test only about 3 % of the time.
- A passing burn-in is not a performance test. AGFHC checks health, not throughput.

## Misconceptions

- *"`amd-smi reset -G -g 3` resets only GPU 3."* On MI35x it resets the hive, all 8 GPUs, and kills every process holding `/dev/kfd`.
- *"GPU index = slot."* No. Use `amd-smi list -e` and the OAM ID.
- *"No lines in dmesg means no errors."* The ring buffer wraps. Read `journalctl -k`.
- *"0 % GFX means the GPU is free."* Look at VRAM and `amd-smi process`, then the [claim](/learn/gpu-process-to-pod/).
