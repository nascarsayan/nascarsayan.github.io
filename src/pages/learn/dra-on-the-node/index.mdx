The scheduler only *records* an allocation in a ResourceClaim. On the node, the kubelet and the vendor's **kubelet plugin** turn that record into device files in a container. This page follows that path on `gpu-node-1`, with the AMD DRA driver v1.0.1 and kubelet 1.35 (illustrative example output).

## The idea

Think of the kubelet as a hotel **front desk** and the DRA driver as the **GPU specialist** on call. The specialist leaves a phone number in the desk's directory (a socket in `plugins_registry`). When a guest (a Pod) arrives with a booking (an allocated claim), the desk calls the specialist: "prepare room `gpu-5-132` for claim `c1a10001`". The specialist sets it up and hands back a key card (the CDI names). Both keep a ledger of who is in which room, so either can be restarted without forgetting.

| Piece | Question it answers |
| --- | --- |
| Registration socket | How does the kubelet find the driver at all? |
| ResourceSlice | What GPUs exist on this node? (published by the driver) |
| `NodePrepareResources` | Make *this* claim's device usable; what should the container get? |
| Two checkpoints | After a restart, which claims are already prepared? |
| 30 s wiping delay | How long does the kubelet trust a driver that went away? |

Where the analogy breaks: once the container is running, the specialist is not needed. The device files stay even if the driver dies. The driver matters only when a container is created or a claim is released.

## Worked example: the kubelet prepares claim c1a10001

The same prefill Pod as on [GPU allocation](/learn/k8s-gpu-allocation/) and [CDI](/learn/cdi-device-injection/). Files and log lines are illustrative example output in the driver's format; the two gRPC messages are rebuilt from the checkpoints (same fields as `api.proto`), since the wire messages are not logged.

The whole conversation, including unprepare, as one sequence:

<Diagram spec={seq} title="Registration, Pod start and Pod stop" autoSteps />

**Prepare fails** (driver down, timeout, error): the Pod stays in `ContainerCreating` with an event, and the kubelet retries. Nothing is rescheduled: the claim is already allocated to this node. The helper documentation also asks the driver to be the last line of defence and refuse a device already prepared for another claim.

**Unprepare** runs when the **last** Pod on the node that uses a claim has stopped. The driver deletes the CDI file and the `checkpoint.json` entry; the kubelet drops its record, and the resourceclaim controller frees the allocation in the API. A kubelet reconcile loop (every 60 s) retries unprepare for claims whose Pods are gone. Until unprepare succeeds the Pod is **not** reported terminated, so the GPU cannot be given to someone else.

Both checkpoint files carry a checksum, so a hand-edited or truncated file fails the check.

## The driver Pod

The AMD GPU operator renders the DRA driver as DaemonSet `kube-amd-gpu/default-dra-driver`. The parts that matter (example, trimmed):

```yaml
spec:
  updateStrategy:
    rollingUpdate: {maxSurge: 0, maxUnavailable: 1}   # old Pod stops before new starts
  template:
    spec:
      priorityClassName: system-node-critical
      nodeSelector: {example.com/gpu-vendor: AMD}
      tolerations: [{operator: Exists}]               # runs even on tainted nodes
      initContainers:
      - name: driver-init                              # wait for the amdgpu module
        command: [sh, -c, 'while [ ! -d /sys/class/kfd ] || [ ! -d /sys/module/amdgpu/drivers/ ]; do echo "amdgpu driver is not loaded "; sleep 2; done']
      containers:
      - name: plugin
        image: registry.local/rocm/k8s-gpu-dra-driver:v1.0.1
        command: [gpu-kubeletplugin]
        env:
        - {name: CDI_ROOT, value: /var/run/cdi}
        - {name: KUBELET_REGISTRAR_DIRECTORY_PATH, value: /var/lib/kubelet/plugins_registry}
        - {name: KUBELET_PLUGINS_DIRECTORY_PATH, value: /var/lib/kubelet/plugins}
        - name: NODE_NAME
          valueFrom: {fieldRef: {fieldPath: spec.nodeName}}
        securityContext: {privileged: true}
        volumeMounts:          # all hostPath
        - {name: plugins-registry, mountPath: /var/lib/kubelet/plugins_registry}
        - {name: plugins,          mountPath: /var/lib/kubelet/plugins}
        - {name: cdi,              mountPath: /var/run/cdi}
        - {name: dev,              mountPath: /dev}
        - {name: sys,              mountPath: /sys}
```

Read it as a list of facts:

- **It needs the host driver first.** The init container loops until `/sys/class/kfd` and `/sys/module/amdgpu/drivers/` exist. A node with a broken `amdgpu` install shows the driver Pod stuck in `Init:0/1` and no ResourceSlice.
- **It runs everywhere it is selected.** `operator: Exists` tolerates every taint, so tainting a GPU node (for example with a not-ready taint) does not stop the DRA driver. That is deliberate: Pods that are already running must still be unprepared when they end.
- **It is privileged** and mounts `/dev` and `/sys` from the host, because it reads GPU topology from sysfs.
- **No liveness probe.** The driver has a gRPC health server, but its `--healthcheck-port` defaults to `-1` (off) and the DaemonSet sets no probe. A driver that hangs without exiting is not restarted. Kubernetes recommends a liveness probe on the driver's health socket.

Images come from `registry.local` with `IfNotPresent`, so a plain restart is usually well under 30 s (in the example, the last driver Pod went from creation to running in about 1 s).

**A kubelet restart** is worse for visibility: at start-up kubelet 1.35 deletes **all** ResourceSlices of its node, for every driver, then waits for drivers to re-register and republish. The node's GPUs vanish from the API for a few seconds.

<Callout tone="warn" title="Upgrades: checkpoint and naming must be compatible">
The new driver must understand the old `checkpoint.json` and name devices the same way (`gpu-<card>-<render>`). If not, it cannot unprepare claims prepared by the old version, CDI files leak, and a restarted container may fail with an unresolvable CDI device. The AMD repo carries a checkpoint upgrade test (`ckpt_upgrade_test.go`), but cross-version behaviour on your nodes is yours to verify before a rollout.
</Callout>

### Why no overlap

Kubelet 1.33+ supports **seamless upgrades**: two instances of a driver run side by side with socket names made unique by the Pod UID, and the kubelet may use either. A driver opts in with the helper's `RollingUpdate(podUID)` option and a DaemonSet that allows surge. The AMD driver v1.0.1 does not pass that option, so it uses fixed socket names, and `maxSurge: 0` keeps two Pods from fighting over them. The cost is the gap above, on one node at a time (`maxUnavailable: 1`).

## Draining and maintenance

- **Stop the DRA driver last.** If it goes before the GPU Pods, they cannot be unprepared and hang in `Terminating`. Kubernetes' guidance is to check that no allocated or reserved claims remain on the node before stopping the driver.
- `kubectl drain` skips DaemonSet Pods (with `--ignore-daemonsets`), so the driver stays. Custom drain scripts that delete everything in `kube-amd-gpu` get this wrong.
- **Readiness gate.** A node-level readiness check can verify that the kubelet has `gpu.amd.com` registered and that complete ResourceSlice pools list as many distinct PCI addresses as the GPU model expects (8 for MI355X), and taint the node `NoSchedule` until they do.

## NVIDIA

NVIDIA's DRA driver (`gpu.nvidia.com`) uses the same kubelet protocol and helper library. Differences: its CDI specs also mount host driver libraries and run hooks, it publishes MIG devices as `mig.nvidia.com`, and its **ComputeDomain** kubelet plugin prepares IMEX channels for NVLink across trays. See [GPU operators](/learn/gpu-operators/).

## Look for yourself

```shell
# on the GPU node (read-only)
ls -la /var/lib/kubelet/plugins_registry /var/lib/kubelet/plugins/gpu.amd.com /var/run/cdi
python3 -m json.tool /var/lib/kubelet/plugins/gpu.amd.com/checkpoint.json | head -40
journalctl -u kubelet --since -1h | grep -iE 'resourceclaim|NodePrepare|dra'
# from the management node
kubectl -n kube-amd-gpu get ds default-dra-driver -o wide
kubectl -n kube-amd-gpu logs <dra-driver-pod> -c plugin | head -20
kubectl get resourceslices --field-selector spec.nodeName=<node>
```
