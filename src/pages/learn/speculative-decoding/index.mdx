[Decode](/learn/decode-phase/) makes one token per step, and each step is limited by reading weights and KV from memory, not by arithmetic. So a decode step has plenty of spare compute. **Speculative decoding** spends that spare compute to make several tokens per step, without changing what the model outputs.

## The idea

**A junior drafts, a senior reviews.** Writing is slow because the senior (the big **target** model) has to "open the whole file" for every single word: one full read of its weights per token. Reading a few proposed words costs the senior almost the same as writing one, because opening the file is the expensive part. So let a fast junior (a small **draft** model) write the next few words, and have the senior check them all in one sitting. The senior keeps the words it would have written itself and replaces the first one it disagrees with.

| Piece | What it is for | The question it answers |
| --- | --- | --- |
| Draft model | cheap guesses | "What are the next $$k$$ tokens, probably?" |
| One target pass over $$k + 1$$ positions | the check, at the price of one decode step | "What would the target have said at each position?" |
| Accept/reject rule | keep the target's answer exactly | "Do I keep this guess?" |
| Acceptance rate $$\alpha$$ | how often guesses survive | "How much faster will this be?" |

**Why checking is cheap.** A forward pass predicts the next token at **every** input position at once (that is how prefill works). Feed the target the current token plus the $$k$$ guesses and it returns its own predictions after each prefix, in one pass that reads the weights once.

**Where the analogy breaks.** The review is not a judgement call: it is exact arithmetic on probabilities, so the output is exactly what the target alone would produce (same distribution). And one rejection throws away **every** guess after it, because those guesses were built on a word that is no longer there.

Every round yields at least one token (the correction or, if all $$k$$ survive, a **bonus** token from the last distribution) and at most $$k + 1$$.

## How much faster

Let $$\boldsymbol{\alpha}$$ be the **acceptance rate**: the chance a draft token survives, assumed equal at every position. For a sampled draft token it is $$\sum \min(p, q)$$ over the vocabulary; in the example above that is {ex.alphaPos.join(', ')} at the four positions, about {ex.alphaMean} on average. From [Leviathan et al.](https://arxiv.org/abs/2211.17192):

$$
\begin{aligned}
\text{expected tokens per round} \quad E &= \frac{1 - \alpha^{k+1}}{1 - \alpha} \\
\text{cost of a round} \quad &= k\,c + 1 \qquad \left(c = \frac{\text{draft step cost}}{\text{target step cost}}\right) \\
\text{expected speedup} \quad S &= \frac{E}{k\,c + 1}
\end{aligned}
$$

- **$$\alpha$$ matters most.** A draft that agrees 80% of the time is worth far more than a slightly cheaper one.
- **Longer guesses have diminishing returns.** All of the first $$i$$ guesses survive with chance $$\alpha^i$$, so late guesses are rarely used, while each costs a draft step. Move $$k$$ in the calculator and watch the curve flatten, then fall.
- **Acceptance depends on the text.** Code, boilerplate and repeated context are easy to guess; creative text is hard. Speedup varies per request.

## When it helps less

- **At large batch sizes.** The cheap check assumes spare compute. A big decode batch already uses more of it, and verifying $$k + 1$$ positions for every sequence multiplies the work. Gains shrink as load grows; some servers adapt $$k$$ or turn speculation off under load (vLLM lists "dynamic speculative decoding").
- **With a poorly matched draft.** Low $$\alpha$$ makes each round cost more than it returns ($$S$$ below 1 in the calculator).
- **Memory.** The draft's weights and its own KV cache take space.

## Variants

| Method | Where guesses come from |
| --- | --- |
| **Draft model** | a separate small LM with the same tokenizer (the original method) |
| **Medusa** | extra prediction heads on the target that guess tokens t+2, t+3… from its last hidden state |
| **EAGLE** | a light draft head (about one transformer layer) that runs autoregressively on the target's **hidden states** rather than on tokens alone; candidates form a **tree** verified in one pass with a tree-shaped attention mask |
| **EAGLE-2** | same, but grows the tree dynamically where the draft is confident |
| **EAGLE-3** | fuses low-, mid- and high-level target features and trains the head on its own predictions, improving acceptance at longer depths |
| **MTP** (multi-token prediction) | modules trained with the model itself to predict further ahead (DeepSeek-V3), reused as the draft |
| **N-gram / prompt lookup** | copy a continuation of the last few tokens from earlier in the prompt; free, good for edits and RAG |

vLLM supports, among others, draft models, EAGLE, MTP, n-gram and suffix decoding ([docs](https://docs.vllm.ai/en/latest/features/speculative_decoding/)). EAGLE-style heads usually get higher $$\alpha$$ than a separate draft model of similar cost because they see the target's internal features.

## Why it means two prefills in a disaggregated server

Both models need the prompt's KV cache before the first round: the draft to make its first guess, the target to verify. A server that runs prefill and decode on separate machines therefore needs **two prefill pools**, one per model, and the decode side receives KV from both.

- **The draft pool is cheaper.** A draft with a few layers prefills several times faster than a 36-layer target and sends far less KV (one transfer per layer), so it needs fewer replicas.
- **Both pools gate the first token.** A request needs a target prefill *and* a draft prefill before decode can start, so a shortage in either pool raises TTFT for everyone. The smaller draft pool loses a larger share of its capacity when one node fails; spreading both pools across nodes matters.

Acceptance rates are measured on the decode side. vLLM-based decoders export `vllm:spec_decode_num_accepted_tokens_per_pos`.

## Common misconceptions

- **"Speculative decoding trades quality for speed."** With the standard rejection rule the output distribution is the target's (step 7 above). Only explicitly lossy variants change it.
- **"The draft writes the answer."** The target decides every token; the draft only proposes.
- **"Speedup = k."** Speedup is $$E / \text{cost}$$, usually 1.5–3× in practice, and it varies with the text and the load.
