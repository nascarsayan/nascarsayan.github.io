This track is for a Linux and Kubernetes engineer who has never had to care what is inside a GPU. Read the pages in the order below; each builds on the one before. Every page puts AMD (MI355X) next to NVIDIA (Blackwell Ultra in HGX/DGX B300 and GB300 NVL72), and uses illustrative read-only output from an example 8-GPU MI355X server.

## The idea first

Think of one GPU as a **factory with its own warehouse**, sitting in a business park (the server). The track answers, in order, the questions you would ask about such a factory:

| Question | Everyday version | Page |
| --- | --- | --- |
| What is inside? | thousands of identical workstations next to a very fast warehouse | [What a GPU is](/learn/what-is-a-gpu/) |
| How is the material packed? | smaller boxes ship faster but hold less detail | [Number formats](/learn/gpu-number-formats/) |
| How does it start up? | the factory's own staff (firmware) open it before the head office (Linux driver) arrives | [Boot and firmware](/learn/gpu-boot-and-firmware/) |
| How does material arrive? | conveyor belts inside, roads between buildings, the motorway to other parks; each ten times slower | [Memory and interconnects](/learn/gpu-memory-and-interconnects/) |
| Which road is nearest? | every factory has its own loading dock and its own on-ramp; use that one | [Node topology](/learn/gpu-node-topology/) |
| Who gives the orders? | the head office (host) owns the building rules; each tenant (container) brings its own tools | [Software stack](/learn/gpu-software-stack/) |
| Can tenants share it? | split the factory into sealed halves or eighths | [Partitioning](/learn/gpu-partitioning/) |

Where the picture breaks: a real factory runs many different jobs; a GPU runs the same instruction on many numbers at once, and is happiest when the job is one giant matrix multiply.

## The picture in seven steps

1. **The chip.** A GPU package is several dies: on MI355X, 8 compute dies (XCDs, 256 CUs) stacked on 2 I/O dies, with 8 HBM3E stacks (288 GB, 8 TB/s) beside them; on Blackwell Ultra, 2 large dies with up to 160 SMs and the same 288 GB and 8 TB/s. It draws up to 1,400 W, throttles when hot, and sits in a server as a PCIe "device" next to the "host" CPUs. → [What a GPU is](/learn/what-is-a-gpu/)
2. **The numbers.** Matrix engines run faster on narrower numbers: FP8 doubles BF16 throughput, and 4-bit formats with per-block scales (OCP MXFP4, NVIDIA NVFP4) double it again while halving memory. The format is a model-quality choice as much as a hardware one. → [Number formats](/learn/gpu-number-formats/)
3. **The boot.** Firmware on the card (AMD IFWI with PSP and SMU; NVIDIA VBIOS with GSP) starts before Linux; the kernel driver then loads microcode, joins the GPU-to-GPU fabric, and creates device files. A kernel launch is a packet in a memory queue plus a doorbell write: the driver never sees it. → [Boot and firmware](/learn/gpu-boot-and-firmware/)
4. **The links.** Bytes cross HBM (8 TB/s), then scale-up links between GPUs (XGMI full mesh of 8 on AMD, about 0.5 TB/s each way per GPU; NVLink through NVSwitch, 0.9 TB/s each way, up to 72 GPUs in NVL72), then PCIe (64 GB/s), then RDMA NICs (50–100 GB/s). Each step is roughly ten times slower and is its own fault domain: an AMD hive reset takes all 8 GPUs. → [Memory and interconnects](/learn/gpu-memory-and-interconnects/)
5. **The layout.** Each GPU on an 8-GPU MI355X server shares a PCIe switch, a NUMA node and one 400G NIC. Index numbers do not line up (GPU 0 pairs with <code>{g0.netdev}</code>, not a NIC numbered 0), so read the map with `lspci`, sysfs and `amd-smi topology`, or `nvidia-smi topo -m`. → [Node topology](/learn/gpu-node-topology/)
6. **The software.** Firmware, kernel driver and device files are on the host and shared; runtime, libraries and frameworks ship in the image. Versions must match across the boundary (ROCm compatibility matrix; CUDA minor and forward compatibility). Anything below the line means draining the node. → [Software stack](/learn/gpu-software-stack/)
7. **The split.** One card can become several logical GPUs: AMD SPX to CPX along XCD lines and NPS1/NPS2 along IOD lines; NVIDIA MIG in sevenths and eighths. Large models use whole GPUs (SPX/NPS1); repartitioning is node maintenance and changes what "one GPU" means everywhere. → [Partitioning](/learn/gpu-partitioning/)

## AMD ↔ NVIDIA name map

| Idea | AMD | NVIDIA |
| --- | --- | --- |
| Compute die | XCD (8 per MI355X) | die (2 per Blackwell) |
| I/O and cache die | IOD (2 per MI355X) | (on the same die) |
| Compute block | Compute Unit (CU) | Streaming Multiprocessor (SM) |
| Lockstep thread group | wavefront (64) | warp (32) |
| Matrix engine | Matrix core | Tensor Core |
| On-card security / management processor | PSP, SMU | GSP |
| Board firmware | IFWI in a PLDM bundle | VBIOS in a firmware bundle |
| GPU-to-GPU link | XGMI / Infinity Fabric | NVLink (+ NVSwitch) |
| Group of linked GPUs | hive | NVLink domain |
| Fabric control software | (none; driver) | Fabric Manager, NVLSM, IMEX |
| Kernel driver | `amdgpu` (+ KFD) | `nvidia` (+ `nvidia-uvm`, `nvidia-peermem`) |
| Compute device file | `/dev/kfd` + `/dev/dri/renderD*` | `/dev/nvidiactl` + `/dev/nvidiaN` |
| User-space runtime | ROCr + HIP | `libcuda` (host) + CUDA runtime |
| Programming model | HIP | CUDA |
| Software platform | ROCm | CUDA toolkit |
| Version rules | ROCm compatibility matrix | CUDA minor / forward compatibility |
| Collective library | RCCL | NCCL |
| Node CLI | `amd-smi` (older: `rocm-smi`) | `nvidia-smi` |
| Topology view | `amd-smi topology` | `nvidia-smi topo -m` |
| Health and metrics daemon | device-metrics-exporter (amd-smi library) | DCGM + dcgm-exporter |
| Hardware validation | RVS, AGFHC | DCGM diagnostics (`dcgmi diag`), field diag |
| Partitioning | compute (SPX…CPX) + memory (NPS) modes | MIG (+ MPS, time-slicing) |
| Retired memory | bad pages (`amd-smi bad-pages`) | row remapping |
| Fault report | RAS / ECC events in the kernel log | Xid errors in the kernel log |
| Kubernetes operator | AMD GPU Operator (`DeviceConfig`) | NVIDIA GPU Operator (`ClusterPolicy`) |
| DRA driver name | `gpu.amd.com` | `gpu.nvidia.com` |
