[GPU allocation in k8s](/learn/k8s-gpu-allocation/) gave the big picture. This page opens each DRA object, field by field, using illustrative example objects of a sample cluster (Kubernetes 1.35, AMD DRA driver v1.0.1). YAML is trimmed: `managedFields`, UIDs and resource versions are removed.

## The idea

DRA is a small ordering system with four forms and one clerk. Each object answers one question:

| Object | Everyday picture | Question it answers | Who writes it |
| --- | --- | --- | --- |
| **ResourceSlice** | a store's shelf inventory | What GPUs are on this node, and what is each like? | the DRA driver |
| **DeviceClass** | a product category | What counts as "an AMD GPU"? | the operator chart (admin) |
| **ResourceClaimTemplate** | a blank order form | What will each Pod of this workload need? | the workload owner |
| **ResourceClaim** | the filled-in order, with the item number stamped on it | What does this Pod need, and which GPU did it get? | controller (spec), scheduler (status) |

The **scheduler** is the clerk: it walks the shelves in a fixed order and takes the first item that fits the category and the order (first fit). Click the i on a box for more.

Where the picture breaks: nothing is shipped. The GPU stays in its slot; the *Pod* is sent to the GPU's node. The stamp is a reservation that lasts as long as the claim. And the shelf list is rewritten by the driver whenever it likes, so editing it by hand does nothing.

## The identity of a device

DRA names a device with three strings: **(driver, pool, device)**.

- **driver**: `gpu.amd.com`. One DRA driver, one name, in DNS-subdomain form (max 63 characters).
- **pool**: a group of devices the driver manages together. The AMD driver uses one pool per node, named after the node: `gpu-node-1`.
- **device**: unique inside the pool. The AMD driver uses `gpu-<card>-<render>`, from the GPU's DRM device numbers: `gpu-5-132` is `/dev/dri/card5` plus `/dev/dri/renderD132`.

The triple is what a claim records. It is stable only as long as the driver names devices the same way. The PCI address in the `resource.kubernetes.io/pciBusID` attribute ties a device to a physical slot, which is what you want for hardware tickets.

## DeviceClass

A **DeviceClass** is a cluster-scoped, named filter over devices. Admins or drivers create it; workloads refer to it by name. The AMD operator chart creates this one:

```yaml
apiVersion: resource.k8s.io/v1
kind: DeviceClass
metadata:
  name: gpu.amd.com
  labels:
    app.kubernetes.io/managed-by: Helm
    helm.sh/chart: gpu-operator-charts-v1.5.1
spec:
  selectors:
  - cel:
      expression: device.driver == 'gpu.amd.com'
```

- `spec.selectors`: CEL expressions. A device belongs to the class only if **all** of them are true.
- `spec.config` (not used here): opaque, driver-specific parameters passed to the driver for every device allocated through this class.
- Being cluster-scoped, a class is also a policy point. An admin can create a narrower class, for example `mi355x-whole` with an extra selector on `productName` and `type`, and allow only that class in some namespaces through admission policy.

## ResourceSlice

A **ResourceSlice** is the driver's inventory. The driver owns it; any manual edit is overwritten. The AMD driver writes one slice per node, owned by the Node object, so deleting the Node deletes the slice.

```yaml
apiVersion: resource.k8s.io/v1
kind: ResourceSlice
metadata:
  name: 00000-gpu.amd.com-gpu-node-1-x7q2m
  generateName: 00000-gpu.amd.com-gpu-node-1-
  ownerReferences:
  - {apiVersion: v1, kind: Node, name: gpu-node-1, controller: true}
spec:
  driver: gpu.amd.com
  nodeName: gpu-node-1          # only this node can use these devices
  pool:
    name: gpu-node-1
    generation: 1                    # bumped when the pool changes
    resourceSliceCount: 1            # slices that make up this pool
  devices:
  - name: gpu-5-132
    attributes:
      type:              {string: amdgpu}               # full GPU, not a partition
      productName:       {string: Instinct_MI355X_OAM}
      deviceID:          {string: "0x75a3"}             # PCI device ID
      driverVersion:     {version: 6.14.0}              # semver type
      driverVersionFull: {string: 6.14.0.70000}
      partitionProfile:  {string: spx_nps1}
      numaNode:          {int: 1}
      resource.kubernetes.io/pciBusID: {string: "0000:8b:00.0"}
      resource.kubernetes.io/pcieRoot: {string: pci0000:80}
    capacity:
      memory:       {value: 294912Mi}    # 288 GiB of HBM
      computeUnits: {value: "256"}
      simdUnits:    {value: 1Ki}
  # … 7 more devices
```

Field notes:

- **Node access.** Exactly one of `nodeName`, `nodeSelector`, `allNodes` or `perDeviceNodeSelection` says which nodes can reach the devices. GPUs are local, so `nodeName`. A network-attached device could use `allNodes: true`.
- **Pools and generations.** A large pool may span several slices. The scheduler uses a pool only when it sees all `resourceSliceCount` slices with the newest `generation`. A half-published pool is ignored, which prevents allocation from a stale inventory.
- **Typed attributes.** Each attribute is one of `string`, `int`, `bool` or `version` (semver). `driverVersion` is a `version`, so CEL can compare it with `semver()`. Unqualified names (`numaNode`) belong to the driver's domain. Qualified names (`resource.kubernetes.io/pciBusID`) are shared, standard attributes so different drivers can be aligned.
- **Capacities** are Kubernetes quantities. `294912Mi` is 294912 ÷ 1024 = 288 GiB; the node label says `288G`.
- **Limits.** A slice holds at most 128 devices (64 if it uses taints or shared counters). Each device has at most 32 attributes plus capacities.
- **The `00000-` prefix.** The scheduler is first fit and walks slices and pools in name order. The `kubeletplugin` helper library prefixes names so that the order matches the driver's wish.

The driver logs the same content when it publishes. In example output, a fresh driver Pod on `gpu-node-3` prints `Discovered 8 AMD GPU devices` and then `Publishing ResourceSlice: {"Pools": {"gpu-node-3": …}}`.

## ResourceClaimTemplate

A **ResourceClaimTemplate** is a namespaced blueprint. Each Pod that references it gets its own claim. The template for the prefill model:

```yaml
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: llm-prefill-gpu
  namespace: gpu-demo
  labels:
    example.com/model-id: gpt-oss-120b
spec:
  spec:                         # the ResourceClaim spec to stamp out
    devices:
      requests:
      - name: gpu               # request name; referenced in results
        exactly:
          deviceClassName: gpu.amd.com
          allocationMode: ExactCount
          count: 1
```

And the Pod side, from the Deployment's Pod template:

```yaml
spec:
  resourceClaims:
  - name: gpu                                           # name inside the Pod
    resourceClaimTemplateName: llm-prefill-gpu
  containers:
  - name: prefill
    resources:
      claims: [{name: gpu}]                             # this container uses it
      limits: {cpu: "8", memory: 256Gi, rdma/hca_devices: "1"}
```

`spec.resourceClaims` declares the claim for the Pod; `resources.claims` says which containers see the devices. A container that does not list the claim gets no device files.

### Request forms

| Field | Meaning | Status in 1.35 |
| --- | --- | --- |
| `exactly.allocationMode: ExactCount`, `count: N` | N devices that match | GA |
| `exactly.allocationMode: All` | every matching device on one node; fails if any is in use | GA |
| `exactly.selectors[].cel` | extra filter on top of the class | GA |
| `exactly.adminAccess: true` | access devices even if in use (see below) | beta, on |
| `firstAvailable: [...]` | prioritized list: try sub-request 1, else 2, … (max 8) | beta, on |
| `constraints[].matchAttribute` | all devices in the listed requests share an attribute value | GA |
| `config[].opaque` | driver-specific parameters for some requests | GA |

A claim can hold at most 32 requests, 32 constraints and 32 allocated devices.

## CEL selectors

CEL (Common Expression Language) is the same language Kubernetes uses in `ValidatingAdmissionPolicy`. In DRA, each expression sees one object, `device`, with `driver`, `attributes` and `capacity`. Attributes and capacities are grouped by domain.

```yaml
selectors:
# only whole GPUs, not partitions
- cel: {expression: 'device.attributes["gpu.amd.com"].type == "amdgpu"'}
# at least 256 GiB of memory
- cel: {expression: 'device.capacity["gpu.amd.com"].memory.compareTo(quantity("256Gi")) >= 0'}
# driver new enough
- cel: {expression: 'device.attributes["gpu.amd.com"].driverVersion.isGreaterThan(semver("6.12.0"))'}
# a fixed NUMA node
- cel: {expression: 'device.attributes["gpu.amd.com"].numaNode == 1'}
```

Two GPUs on the same PCIe root, written as a constraint:

```yaml
requests:
- name: gpus
  exactly: {deviceClassName: gpu.amd.com, allocationMode: ExactCount, count: 2}
constraints:
- requests: [gpus]
  matchAttribute: resource.kubernetes.io/pcieRoot
```

## ResourceClaim: an allocated one

The resourceclaim controller stamped this claim out of the template for Pod `…-p4x7k`. The scheduler filled in `status`.

```yaml
apiVersion: resource.k8s.io/v1
kind: ResourceClaim
metadata:
  name: llm-prefill-5f7d8c9b6-p4x7k-gpu-z8k3q
  namespace: gpu-demo
  annotations:
    resource.kubernetes.io/pod-claim-name: gpu         # name inside the Pod
  finalizers:
  - resource.kubernetes.io/delete-protection           # no delete while in use
  ownerReferences:
  - {apiVersion: v1, kind: Pod, name: llm-prefill-5f7d8c9b6-p4x7k, controller: true}
spec:                                                  # copied from the template
  devices:
    requests:
    - name: gpu
      exactly: {deviceClassName: gpu.amd.com, allocationMode: ExactCount, count: 1}
status:
  allocation:
    devices:
      results:
      - request: gpu
        driver: gpu.amd.com
        pool: gpu-node-1
        device: gpu-5-132
    nodeSelector:                                      # where the Pod may run
      nodeSelectorTerms:
      - matchFields:
        - {key: metadata.name, operator: In, values: [gpu-node-1]}
  reservedFor:                                         # who uses it now
  - {resource: pods, name: llm-prefill-5f7d8c9b6-p4x7k, uid: b0d10001-…}
```

- `status.allocation.devices.results`: the source of truth for "who has which GPU".
- `status.allocation.nodeSelector`: copied from the slice's node access. Any Pod that uses this claim must run on `gpu-node-1`.
- `status.reservedFor`: consumers, max 256. A claim can be shared by several Pods if they all reference it by name (`resourceClaimName` instead of a template). Template claims are private to one Pod.
- The Pod links back in `status.resourceClaimStatuses: [{name: gpu, resourceClaimName: …-gpu-z8k3q}]`.
- `kubectl get resourceclaims` prints `STATE allocated,reserved`: allocated means `status.allocation` is set, reserved means `reservedFor` is not empty.
- `status.devices` (not used by the AMD driver) lets a driver report per-device conditions or network data. The feature gate `DRAResourceClaimDeviceStatus` is beta and on in 1.35.

## How the scheduler allocates

<Diagram spec={alloc} title="From Pod creation to an allocated claim" caption="Names are from the sample prefill Pod. The scheduler phases are the DynamicResources plugin's extension points. Press play to step through." autoSteps />

1. **PreEnqueue.** The Pod is not even tried until every claim it references exists. A Pod whose template is missing waits here.
2. **PreFilter.** The plugin gathers the Pod's claims. Claims already allocated (shared claims) fix the node. Unallocated claims are collected for allocation.
3. **Filter (per node).** For each candidate node, the plugin runs the allocator over the slices that node can reach. It tries devices in slice and pool name order, checks class selectors, claim selectors and constraints, and skips devices already allocated to other claims or held by Pods in flight. First fit wins; there is no "best GPU" scoring in the base algorithm.
4. **Reserve.** The chosen devices go into an in-memory "in flight" set, so a second Pod scheduled in parallel cannot pick them.
5. **PreBind.** The plugin writes `status.allocation` and adds the Pod to `reservedFor` in the API. If that write fails, `Unreserve` drops the in-memory hold and the Pod is retried.
6. **Bind.** Only now does the Pod get `spec.nodeName`.

Things this implies:

- **Normal scheduling rules still apply.** CPU, memory, node affinity, taints and `rdma/hca_devices` filter nodes before the device check matters. A Pod with a perfect GPU match still fails on a node without 256 GiB of free memory.
- **No preemption for devices.** The scheduler does not evict lower-priority Pods to free a GPU. A full cluster leaves the Pod Pending.
- **Bypassing the scheduler breaks DRA.** A Pod created with `spec.nodeName` already set skips allocation. The kubelet refuses to start it until its claims are allocated and reserved for it.
- **Load.** Every candidate node runs CEL for every device. In a cluster of a few hundred GPUs that is small. The alpha gate `DRASchedulerFilterTimeout` (off in 1.35) can cap a slow filter.

## Admin access

A request with `adminAccess: true` can be allocated a device **that is already in use** by another claim. It exists for monitoring and debugging agents that must see every GPU. The canonical form uses `allocationMode: All` to get every matching device on a node.

- Only allowed in namespaces labelled `resource.kubernetes.io/admin-access: "true"`. The API server rejects it elsewhere.
- Feature gate `DRAAdminAccess`: beta, on by default in 1.34 and 1.35, GA in 1.36.
- The AMD metrics exporter does not need it. It reads GPUs through the host and maps them to Pods through the kubelet's PodResources API.

## Newer features and their status

**Prioritized list (`firstAvailable`).** "Give me one MI355X, else two smaller GPUs." The scheduler tries sub-requests in order. Beta, on in 1.35. Useful for mixed fleets; a single-model fleet does not need it.

**Partitionable devices.** Lets a driver publish overlapping devices (a whole GPU and its partitions) that consume from **shared counters**, so allocating a partition makes the whole GPU unavailable and the other way round. Alpha, off in 1.35 (`DRAPartitionableDevices`), beta from 1.36. The AMD driver v1.0.1 does not create partitions; it publishes whatever mode the GPU is already in (`type: amdgpu` or `amdgpu-partition`). See [GPU partitioning](/learn/gpu-partitioning/).

**Device taints and DeviceTaintRule.** Like node taints, but on one device. Effects: `NoSchedule` (do not allocate), `NoExecute` (also evict Pods using it, done by a controller in kube-controller-manager) and `None` (informational). Drivers can put taints in slices (`DRADeviceTaints`); admins can taint devices without the driver through a cluster-scoped `DeviceTaintRule` (`DRADeviceTaintRules`, served as `resource.k8s.io/v1alpha3` in 1.35). Both are alpha and off in 1.35. A cluster that has not enabled the gate does not serve the API (`kubectl get devicetaintrules` fails). An alpha API carries no upgrade guarantee, so anything built on it must expect changes at 1.36.

**Consumable capacity.** Several claims share one device and each consumes part of a capacity (for example memory). Alpha in 1.35.

**Extended resource mapping.** A DeviceClass can declare `extendedResourceName`, so legacy Pods asking for `amd.com/gpu: 1` are served by DRA. Alpha in 1.35, beta in 1.36.

**Binding conditions.** Delay binding until a device reports ready (for attachable fabric devices). Alpha in 1.35.

## Feature gates in Kubernetes 1.35

From the Kubernetes feature-gate reference. "On" means on by default; nothing on the sample cluster overrides the defaults (no `--feature-gates` on the API server, scheduler or controller-manager, none in the kubelet config).

| Gate | Stage in 1.35 | Default | What it unlocks |
| --- | --- | --- | --- |
| `DynamicResourceAllocation` | GA (since 1.34) | on | the core API and scheduling |
| `DRAAdminAccess` | beta | on | `adminAccess` requests |
| `DRAPrioritizedList` | beta | on | `firstAvailable` |
| `DRAResourceClaimDeviceStatus` | beta | on | `status.devices` |
| `KubeletPodResourcesDynamicResources` | beta | on | DRA devices in the PodResources API |
| `DRAPartitionableDevices` | alpha | off | shared counters |
| `DRADeviceTaints` | alpha | off | taints in slices, tolerations in claims |
| `DRADeviceTaintRules` | alpha | off | `DeviceTaintRule` objects |
| `DRAConsumableCapacity` | alpha | off | shared consumable capacity |
| `DRAExtendedResource` | alpha | off | extended-resource mapping |
| `DRADeviceBindingConditions` | alpha | off | binding conditions |
| `DRASchedulerFilterTimeout` | alpha | off | filter time limit |
| `ResourceHealthStatus` | alpha | off | device health in Pod status |

Alpha gates must be turned on in each component that uses them (API server, scheduler, controller-manager, kubelet), and alpha API versions need `--runtime-config` on the API server.

## Misconceptions

- **"The DeviceClass decides which GPUs a namespace may use."** Only if you build that. By default any namespace may create claims against any class. Access control is RBAC on `resourceclaims` plus admission policy.
- **"Deleting a claim frees the GPU at once."** The `delete-protection` finalizer keeps the claim while it is reserved. The GPU is free after the Pod stops and the kubelet has unprepared it.
- **"Editing a ResourceSlice fixes bad data."** The driver overwrites it. Fix the driver or the node.
- **"The pool name is the node name."** For the AMD driver, yes. It is the driver's choice, not a rule.
