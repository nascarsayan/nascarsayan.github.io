[Prefill](/learn/prefill-phase/) wants many tokens per step to keep the GPU's matrix units busy. [Decode](/learn/decode-phase/) produces one token per sequence per step and wants many sequences per step to share the weight read. Both are solved by **batching**. The part of the server that decides what goes into each step is the **scheduler**.

## The idea

A GPU runs the model in **steps** (also *iterations*): one forward pass over whatever tokens were chosen, every 1 to 100 ms. The scheduler's job is to fill each step well. Think of kube-scheduler with a millisecond cycle: every step it looks at the queue, the free KV memory and the **token budget**, and binds work to the next forward pass.

**An everyday picture: a metro, not a tour bus.**

| | Tour bus (static batching) | Metro (continuous batching) |
| --- | --- | --- |
| Leaves when | it is full | every step, full or not |
| New passengers | wait for the next bus | board at the next stop |
| A passenger who is done | stays on until the last one is done | gets off at the next stop |
| Seats | one per passenger, sized for the longest trip | a fixed number of **tokens** per step, shared |

**Where the analogy breaks.** A prompt is a big group that may not fit one train: it boards in **chunks** over several steps. A decoding request takes one seat per step, every step, until it ends. And each passenger carries luggage that grows every step (its KV cache); when the racks are full, someone is put off the train (**preemption**).

**The questions each part answers:**

- **Token budget** (`max_num_batched_tokens`): how much work fits in one step? Bigger means fewer steps for a prompt, but every step gets longer.
- **Sequence cap** (`max_num_seqs`): how many requests may share one step?
- **Free KV memory**: does this request's new KV fit? If not, it waits, or someone is evicted.
- **Order**: who goes first? vLLM puts running decodes first, so a decoding user never waits behind a whole long prompt.

Both servers did the same useful work ({ex.totalWork} tokens: every prompt token, plus every output token after the first). Continuous batching packs it into fewer steps because nobody waits for a batch boundary. This is the **Orca** idea (*iteration-level scheduling*, OSDI 2022), now standard in vLLM, SGLang and TensorRT-LLM. It depends on [paged KV memory](/learn/kv-cache-management/): requests of very different lengths share a step because each has its own block table, with no padding.

## The rule, and the budget trade

vLLM treats every request the same way: it knows $$N$$ tokens and has computed KV for $$C$$ of them. A step gives it some of the remaining $$N - C$$: one token for a request in decode, as many as fit for a prompt. Each step is limited by:

1. **Token budget**: `max_num_batched_tokens`, for example 8,192 tokens.
2. **Sequence limit**: `max_num_seqs`.
3. **KV memory**: new tokens must fit in free (or evictable) KV blocks.

With chunked prefill on, vLLM fills a step with all **running decodes** first, then **prefills** with the leftover budget ([optimization guide](https://docs.vllm.ai/en/latest/configuration/optimization.html)). The same rule at production scale:

The budget sets the trade-off between the two kinds of user. A small budget (the guide's example is 2,048) keeps steps short, so decoding users get a better **ITL** (inter-token latency); a large one finishes prompts in fewer steps, so new users get a better **TTFT** (time to first token) and the GPU better throughput. ## Head-of-line blocking: three requests, one queue

Take a prefill-only server with an 8,192-token budget. A 30,000-token prompt arrives; about 50 ms later two short prompts (200 and 800 tokens) arrive behind it.

1. **The long prompt takes whole steps.** It needs four chunks: three full 8,192-token steps and a remainder of 5,424. First come, first served gives it the whole budget in steps 1–3.
2. **The short prompts wait.** They need only a few milliseconds of compute, but there is no budget left for them until step 4.
3. **All three share the last step.** Step 4 holds 5,424 + 200 + 800 = 6,424 tokens. The short requests' forward passes end together with the long one's.

The short requests wait for three full steps, a few hundred milliseconds, for work that alone needs a few tens. Chunking bounded each step, but it did not let them jump the queue. Mitigations are policy: a smaller budget, `--long-prefill-token-threshold` (caps a long prompt's share of each step; off by default), `--scheduling-policy priority`, or separate replicas for long prompts. The same effect from the prefill side: [Prefill](/learn/prefill-phase/#head-of-line-blocking).

## Admission, waiting and preemption

- **Queueing.** Requests that do not fit wait. The default order is first-come-first-served; `--scheduling-policy priority` lets each request carry a priority.
- **Preemption.** If running sequences grow and KV blocks run out, the scheduler evicts some (by default it frees their KV and later recomputes it). Victims see a pause; `vllm:num_preemptions` counts them.
- **Load signals.** `vllm:num_requests_running`, `vllm:num_requests_waiting` and `vllm:num_requests_waiting_by_reason` show the queue; `vllm:request_queue_time_seconds` shows how long requests waited.

## Sizing with Little's law

**Little's law** links three long-run averages: $$\text{requests in the system} = \text{arrival rate} \times \text{time in the system}$$. A replica receiving 10 requests per second that spends 50 ms on each has on average **0.5 requests in flight**: busy about half the time, and most engine steps run a single request. Try other rates in the second calculator box above.

Averages hide bursts: the head-of-line example above can happen on a replica that is idle most of the time. Size for peak arrival rate and the latency target, not for the average.

## Disaggregation is a scheduling decision

In an aggregated server every step mixes prefill chunks and decodes, and each hurts the other: a big chunk lengthens the step every decoding user waits for (the calculator's ITL), and a big decode batch takes budget from prefills (its TTFT). [DistServe](https://arxiv.org/abs/2401.09670) and [Splitwise](https://arxiv.org/abs/2311.18677) showed that putting the two phases on **separate** machines removes that interference and lets each side be sized for its own target: TTFT for prefill, ITL for decode.

In a disaggregated server, prefill workers run no decodes, so their scheduler only fits prompts into the token budget, and the decode workers batch decodes on their own. A router picks a prefill worker and a decode worker per request; there need not be a fixed 1:1 mapping between them.

## Routing across replicas

With many replicas, *which* replica gets a request matters as much as how each schedules:

- **Least-loaded**: spread queue depth evenly.
- **Cache-aware**: send a request where its prefix is already cached. When a large share of prompt tokens comes from cache, a routing change that breaks affinity multiplies prefill compute.
- **Length-aware**: keep very long prompts away from replicas serving latency-sensitive short ones (the cure for the head-of-line example).

<Callout tone="note" title="How this shows up when operating a server">
- A replica that is "up" but receives no work shows flat request counters: look at routing, not the GPU.
- Queue time rising while GPU utilization is low points at a scheduler limit (budget, KV, sequence cap) or head-of-line blocking, not a lack of hardware.
- Adding replicas lowers queueing but also spreads the prefix cache thinner unless routing is cache-aware.
</Callout>

## Common misconceptions

- **"Batch size is a fixed setting."** With continuous batching it changes every step; the settings are upper limits.
- **"Bigger batches are always better."** They raise throughput but lengthen each step, which every user in it feels as ITL.
- **"Chunked prefill fixes long prompts blocking short ones."** It stops one giant step; short requests can still wait behind the chunks, as in the example above.
