A large language model (LLM) is one function: it takes a list of tokens and returns, for every possible next token, a probability. Generating text means calling that function again and again, appending the chosen token each time. This page walks through one call, using **gpt-oss-120b**, an open-weight mixture-of-experts model. Its numbers come from its [config.json](https://huggingface.co/openai/gpt-oss-120b/blob/main/config.json) and [model card](https://arxiv.org/abs/2508.10925).

## The idea

Think of the model as an assembly line that works on a **notepad per word**.

- **Tokens** answer "what are the pieces?" Text is cut into pieces from a fixed list (the vocabulary), and each piece is replaced by its number in that list.
- **Embedding** answers "what is a first guess at what this piece means?" Each token number picks one row of a big table: a list of 2,880 numbers, the token's notepad. Similar pieces get similar notepads.
- **Layers** answer "what does this piece mean *here*?" 36 stations each read every notepad and write a small correction on it. In **attention** the notepads compare notes with earlier ones ("which earlier words matter to me?"); in the **MLP** each notepad is processed alone ("given what I now know, what facts apply?").
- **Unembedding and sampling** answer "what comes next?" The last notepad is scored against every vocabulary entry; the scores become probabilities; one token is picked.

Where the analogy breaks: the notepads are not words or facts a person could read. They are vectors of numbers whose meaning is learned, and every layer writes into the same vector (the **residual stream**) instead of a fresh page.

The sampler decides how that distribution becomes one token. Move the sliders:

<Sampler />

- **Greedy**: take the most likely token.
- **Temperature** T: divide logits by T before the softmax. Below 1 sharpens, above 1 flattens.
- **Top-p** (and top-k): sample only from the smallest set whose probabilities sum to p (or the k most likely).

Appending the chosen token and running again is [decode](/learn/decode-phase/). The first pass over the whole prompt is [prefill](/learn/prefill-phase/). A forward pass computes a hidden state for **every** input position; [speculative decoding](/learn/speculative-decoding/) uses the predictions at several positions at once.

## Tokens, in more detail

More real tokenizer output:

{sentences.slice(1).map((s) => <TokenChips text={s.text} tokens={s.tokens} compact />)}

- gpt-oss uses `o200k_harmony`, a **byte-pair encoding** (BPE): start from bytes and repeatedly merge the most common adjacent pairs seen in training, so common words become one token and rare words, code and IDs become several.
- English prose averages roughly 3–4 characters per token. Every cost on these pages (KV cache size, prefill time, price per request) scales with **tokens**, not characters.
- Chat requests are wrapped in the [harmony format](https://cookbook.openai.com/articles/openai-harmony) before tokenizing: special tokens mark system, user and assistant turns. A "short" user message still arrives as a few hundred tokens with the system prompt and template. That shared start is what [prefix caching](/learn/kv-cache-management/) reuses.

## The layer, in more detail

```text
x = x + Attention( RMSNorm(x) )    # tokens exchange information
x = x + MoE_MLP(   RMSNorm(x) )    # each token is processed on its own
```

- **RMSNorm**: `x / sqrt(mean(x²) + 1e-5) * g`, applied before each block ("pre-norm") and once after the last layer.
- **Attention**: query, key and value projections per token; scores against earlier keys; softmax; weighted sum of values. 64 query heads of size 64 share 8 key/value heads (**grouped-query attention**, GQA); an output matrix maps the 4,096 concatenated head outputs back to 2,880.
- **RoPE** (rotary position embedding): attention alone does not know token order. RoPE rotates pairs of numbers in each query and key by an angle proportional to the position, so a query–key dot product depends on their distance. gpt-oss uses `rope_theta` 150,000 and YaRN scaling (factor 32) to stretch a 4,096-token training context to 131,072.
- **Sliding window**: every other gpt-oss layer attends only to the last 128 tokens, which halves the long-context [KV cache](/learn/attention-and-kv-cache/).
- **MLP**: SwiGLU, `down( silu(gate(x)) * up(x) )`, with gate and up mapping 2,880 → 2,880. In gpt-oss each layer has 128 such experts and a router picks 4 per token: 4 × 24.9 M = 99.5 M MLP parameters used per layer, out of 3.2 B. Hence 116.8 B parameters but 5.1 B active. → [Mixture of experts](/learn/mixture-of-experts/)
- **Embedding and unembedding**: two separate 201,088 × 2,880 matrices (`tie_word_embeddings` is false).

## Where the parameters are

Counting from the config (biases and small tensors left out):

<ParamBar />

| Part | Shape per layer | Parameters (all 36 layers) | Used per token |
| --- | --- | --- | --- |
| Attention Q, K, V, O | 2,880×4,096 + 2×(2,880×512) + 4,096×2,880 | ~0.96 B | all |
| Router | 2,880 × 128 | ~0.01 B | all |
| Experts (SwiGLU) | 128 × 3 × 2,880 × 2,880 | ~114.7 B | 4 of 128 per layer: ~3.6 B |
| Embedding | 201,088 × 2,880 | 0.58 B | one row per token |
| Unembedding | 2,880 × 201,088 | 0.58 B | only where a token is predicted |

The model card gives the same split: MLP 114.71 B, attention 0.96 B, embed + unembed 1.16 B, 5.1 B active. Over 98% of the weights are experts, and that is exactly what is stored at 4.25 bits (MXFP4); attention, router and embeddings stay in 16-bit. Hence the 60.8 GiB checkpoint, roughly 65 GB.

For comparison, a dense model such as **Llama 3.3 70B** (80 layers, hidden size 8,192, 64 query and 8 KV heads of size 128) uses all ~70 B parameters for every token, about 141 GB in 16-bit.

## What the hardware actually does

Almost every step is a **matrix multiply**: a $$\text{tokens} \times 2{,}880$$ activation matrix times a weight matrix. A multiply-add counts as 2 floating-point operations (FLOPs), so a linear layer costs about **2 FLOPs per weight per token**.

For gpt-oss-120b, the active weights excluding embeddings are about 4.5 B, so the linear layers cost about **9 GFLOP per token**, plus attention, which grows with context length (worked out on [Prefill](/learn/prefill-phase/)). Llama 3.3 70B costs about 140 GFLOP per token: MoE makes gpt-oss roughly 15× cheaper per token in compute, though it still has to *store* all 117 B parameters.

The two numbers that decide speed on any chip:

- **FLOPs** needed, which matter when many tokens share each weight read (prefill), and
- **bytes** read from memory, which matter when few tokens share each weight read (decode).

That split is why [prefill](/learn/prefill-phase/) and [decode](/learn/decode-phase/) behave so differently. The GPU kernels that do these multiplies are on [Prefill and decode as kernels](/learn/llm-kernels/).

<Callout tone="note" title="How this shows up when serving">
A serving process loads the full checkpoint (about 65 GB for gpt-oss-120b as published) into GPU memory at start-up; one 288 GB MI355X holds it with room left for the KV cache. Load time scales with checkpoint size and storage bandwidth, not with traffic.
</Callout>

## Common misconceptions

- **"A token is a word."** It is a vocabulary entry; `kubectl` is two, `MI355X` three.
- **"Bigger model, slower per token, always."** For MoE models, compute per token tracks *active* parameters (5.1 B), while memory tracks *total* (117 B).
- **"The model remembers the conversation."** It does not. Every request re-sends the whole history as tokens. The server can avoid recomputing it with a [prefix cache](/learn/kv-cache-management/), but that is a cache, not memory in the model.
- **"Only the new token is computed."** In prefill every prompt position runs through every layer. In decode only the new token does, because the [KV cache](/learn/attention-and-kv-cache/) holds the rest.
