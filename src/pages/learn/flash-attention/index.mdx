[Attention and the KV cache](/learn/attention-and-kv-cache/) explains *what* attention computes. This page is about *how* GPU kernels compute it fast. Attention is two matrix multiplies with a softmax in between. The hard part is not the math. It is the size of the matrix in the middle.

## The idea first

**What FlashAttention is for.** Attention compares every token with every earlier token. For a 4,000-token prompt that is a 4,000 × 4,000 sheet of scores per head. The math on that sheet is cheap for a GPU; *writing the sheet to memory and reading it back* is not. FlashAttention computes the same answer without ever writing the sheet down.

**The analogy: a desk and a warehouse.** HBM is a big warehouse, far away. The chip's LDS and registers are a small desk, close by. Naive attention fills the warehouse with the whole score sheet, then walks back and forth to read it. FlashAttention keeps a block of questions (queries) on the desk, has the warehouse send the keys and values over one block at a time, and keeps only **three running notes** per question:

| Note | What it means | The question it answers |
| --- | --- | --- |
| **m** | the best match score seen so far | "What is my reference point?" (softmax needs the row's max) |
| **l** | the total weight of everything seen so far | "What do I divide by at the end?" (softmax's denominator) |
| **o** | the weighted blend of values seen so far | "What is my answer so far?" (the numerator) |

When a better match shows up, the old notes were written relative to the old best, so they are scaled down once (multiply by exp(old m − new m)) and the new block is added. Like converting a running total into a new currency: one multiply, no need to recount what came before.

**Where the analogy breaks.** The desk is tiny (LDS is 160 KB per CU on MI355X), so block sizes are a tuning trade-off, not a free choice. And the result is not an estimate: the running notes give the exact same answer as the full sheet (checked with numbers below).

## The naive version and its problem

For one head, with $$T$$ tokens and head size $$d$$:

1. $$S = Q \cdot K^\top / \sqrt{d}$$. $$Q$$ and $$K$$ are $$T \times d$$, so **$$S$$ is $$T \times T$$**.
2. $$P = \operatorname{softmax}(S)$$, row by row, with future positions masked (causal).
3. $$O = P \cdot V$$, $$T \times d$$.

Take a 4,000-token prompt and gpt-oss-120b's 64 query heads (published config). One head's S in FP32 is 4,000 × 4,000 × 4 B = **64 MB**; all heads of one layer, **4 GB**. A naive implementation writes S to HBM, reads it back for the softmax, writes P, and reads P again for $$P \cdot V$$. That traffic dwarfs the $$4 \times T^2 \times d$$ FLOPs of the two products, so naive attention is memory-bound and its memory use grows with $$T^2$$. Move the sliders to see by how much:

Read the FLOP-per-byte tiles. FlashAttention's intensity stays near the query block size times the GQA group (at most 128 × 8 = 1,024; the Q and O traffic pull it a little lower), whatever the prompt length: each K/V byte it reads is used by every query row of the block and every query head of the group. Naive attention's intensity stays in the tens (about $$d/3$$) because its $$T \times T$$ sheets grow as fast as the math.

## FlashAttention: never store S

**FlashAttention** (Dao et al., 2022) computes exact attention without ever writing S or P to HBM. A workgroup takes a block of query rows, keeps them on chip, and streams K and V through LDS one block at a time. For each K/V block it computes a tile of S in registers, turns it into a tile of P, multiplies by V, and accumulates into O. The $$T \times T$$ matrix exists only one tile at a time.

The obstacle is the softmax. Each row of $$P$$ is $$\exp(s_i - \max) / \sum_j \exp(s_j - \max)$$, and the max and the sum run over the **whole row**, which you have not seen yet when you process the first block.

### The online softmax

The trick (Milakov and Gimelshein, 2018, "online normalizer calculation") is the three running notes from [the idea first](#the-idea-first). Per query row and per K/V block:

```text
m_new = max(m, max_j s_j)
scale = exp(m - m_new)                       # shrink old terms to the new reference
l     = l * scale + sum_j exp(s_j - m_new)
o     = o * scale + sum_j exp(s_j - m_new) * v_j
m     = m_new
# after the last block: output = o / l
```

### The kernel

<Diagram spec={loop} title="FlashAttention forward, one workgroup" caption="Block sizes are typical examples. S and P never leave registers. Step through the messages with the player." autoSteps />

- **Grid:** one workgroup per (query block, head, sequence). A 4,000-token prompt with 128-row query blocks and 64 heads gives 32 × 64 = 2,048 workgroups: plenty for 256 CUs.
- **Two GEMMs per K/V block** run on the matrix cores (`v_mfma_*` on AMD, `mma` / `wgmma` / `tcgen05.mma` on NVIDIA). The softmax steps (max, exp, scale) run on the ordinary vector ALUs, which are many times slower per FLOP than matrix cores. Keeping that part small and overlapped is most of the tuning work.
- **Causal masking** skips K/V blocks entirely above the diagonal: roughly half the work for prefill.
- **Grouped-query attention (GQA):** gpt-oss has 64 query heads but only 8 KV heads, so 8 query heads read the same K and V. Kernels load a K/V block once and use it for all 8.
- **Sliding window:** gpt-oss alternates `sliding_attention` layers (window 128 tokens) with `full_attention` layers (published config). In sliding layers each query only visits the last 128 keys, so the K/V loop is a few blocks long however long the prompt is.

HBM traffic is now roughly: read Q once, read K and V once per query block, write O once. Prefill attention becomes compute-bound for long prompts, like a GEMM.

### Generations

| Version | What changed (from the papers) |
| --- | --- |
| FlashAttention (2022) | IO-aware tiling; S never written to HBM; memory linear in T |
| FlashAttention-2 (2023) | fewer non-matmul FLOPs; one head split across thread blocks; better work split between warps. About 2× FlashAttention: 50–73 % of A100 peak, up from 25–40 % |
| FlashAttention-3 (2024) | Hopper-specific: asynchronous Tensor Cores and TMA, warp specialization, softmax interleaved with matmul, FP8. 1.5–2× FlashAttention-2 on H100 |

On AMD, FlashAttention-style kernels come from Composable Kernel (CK), AITER and Triton. vLLM picks one per platform; see the backend list below.

<Callout tone="note" title="Misconception: FlashAttention is an approximation">
It computes the same result as the textbook formula, up to floating-point rounding. It is faster because it moves less data, not because it computes less.
</Callout>

## Decode: paged attention

In decode each sequence brings **one** new query token per step, and its keys and values sit in the KV cache. Two things change.

**1. The shape is a matrix-vector product.** Per head, $$q$$ is $$1 \times d$$ and $$K$$ is $$n \times d$$ for $$n$$ cached tokens. There is no reuse of K or V within a sequence: each cached byte is used once per step. For gpt-oss with 16-bit KV, each cached token is 2 × 8 KV heads × 64 × 2 B = 2,048 bytes per layer and yields about 16,000 FLOPs across the 64 query heads: **≈8 FLOP/B**, far below any ridge point. Decode attention speed is set by how fast the kernel streams the KV cache from HBM. → [Roofline](/learn/gpu-memory-hierarchy/#apply-it-to-an-llm)

**2. The KV cache is paged.** vLLM stores K and V in fixed-size **blocks** (for example 16 tokens) scattered across HBM, with a **block table** per sequence that lists its block numbers in order, like a page table (PagedAttention, Kwon et al., 2023). The attention kernel follows the table:

```text
// Illustrative inner loop of a paged decode kernel, one workgroup = one (sequence, KV head)
for (logical_block = 0; logical_block < num_blocks(seq); logical_block++) {
  phys  = block_table[seq][logical_block];          // indirection, like a page table
  K_blk = key_cache[phys][kv_head];                  // e.g. 16 tokens x 64 dims
  V_blk = value_cache[phys][kv_head];
  s     = q[8 query heads] . K_blk^T / sqrt(d);      // GQA: 8 queries share this K
  online-softmax update of (m, l, o) with s and V_blk
}
out[seq][8 query heads] = o / l
```

### Too few workgroups: split-KV

One workgroup per (sequence, KV head) gives a batch of 4 sequences × 8 KV heads = **32 workgroups** for 256 CUs. Long contexts make each of those workgroups long and the GPU mostly idle. **Split-KV** (also called Flash-Decoding) splits each sequence's KV cache into chunks, runs one workgroup per chunk, and then a small reduction kernel combines the partial (m, l, o) triples, using the same rescaling as the online softmax (step 6 of the walkthrough). This is the attention version of [split-K](/learn/gemm-tiling/#when-there-are-not-enough-tiles).

### Mixed batches

Servers like vLLM V1 batch prefill chunks and decode tokens from different requests into one step. Their attention backends therefore take a **variable number of query tokens per sequence** (thousands for a prefill chunk, one for a decode) over the same paged KV cache, and pick tiling per sequence inside one launch.

## How this shows up in operations

- **Long prompts cost quadratically in prefill attention, linearly in KV memory.** TTFT for a 32k-token prompt is dominated by attention far more than for a 4k prompt. → [Prefill](/learn/prefill-phase/)
- **KV-cache block size and layout are part of the contract** between prefill and decode in disaggregated serving: the KV transfer must reorder blocks into the decode side's layout.
- **Backend choice is a start-up decision.** A different image, vLLM version or environment variable can switch the attention backend and change speed with no code change.
