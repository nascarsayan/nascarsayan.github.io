## The idea

Kubernetes has no idea what a GPU is. Four separate pieces of software teach it, and each one fails in its own way:

- an **installer** (the AMD GPU operator) that puts the GPU agents on every GPU node;
- a **booking system** (DRA) that knows every GPU by name and gives each Pod one, like a theatre seat;
- a **fitter** (the DRA driver on the node, plus CDI in containerd) that makes the booked GPU's device files appear inside the container, and nothing else;
- a **cabler** (Multus plus the RDMA device plugin) that gives the Pod a second network interface and RDMA access to a 400G NIC.

If you know Kubernetes well, the short version is: **GPUs are allocated like PersistentVolumeClaims (DRA), injected like CSI volumes (a kubelet plugin over gRPC, then CDI), installed by an operator, and networked through Multus plus a device plugin.** The analogy with storage breaks in one place: there is no external provisioner. The scheduler itself picks the device.

## Which object answers which question

| Question | Look at |
| --- | --- |
| Which GPUs exist on a node, and what are they? | `kubectl get resourceslices --field-selector spec.nodeName=<node> -o yaml` |
| Which Pod holds which GPU? | `kubectl get resourceclaims -A -o wide`, then `status.allocation.devices.results` |
| Is the driver registered on the node? | `/var/lib/kubelet/plugins_registry/gpu.amd.com-reg.sock`; a ResourceSlice exists for the node |
| Did the device files reach the container? | `/var/run/cdi/*_<claim-uid>.yaml` on the node; the driver's `checkpoint.json` |
| Which operands are on and at which version? | `kubectl -n kube-amd-gpu get deviceconfig default -o yaml`, `get ds -o wide` |
| Does the Pod have its data network? | Pod annotation `k8s.v1.cni.cncf.io/network-status` |
| Is the node fit for new GPU Pods? | `Ready` condition, no `NoSchedule` taints, a ResourceSlice with all GPUs |

```shell
kubectl get nodes -l example.com/gpu-node -o wide
kubectl -n kube-amd-gpu get deviceconfig,ds,deploy
kubectl get deviceclass,resourceslices
kubectl get resourceclaims -A -o wide
kubectl get pods -A -o wide --field-selector spec.nodeName=<gpu-node>
kubectl get net-attach-def -A
```

## The sample cluster's choices, in one place

- **DRA only**, device plugin off; whole GPUs, SPX/NPS1, one claim per Pod.
- **Host driver and ROCm in the OS image** (`amdgpu-dkms`), not from the operator (`driver.enable: false`); NFD, KMM, partitioning, remediation and test runner off.
- **Readiness** through node conditions and a `NoSchedule` taint while a check fails, with DRA driver registration as one of the checks.
- **Data network** through file-backed Multus NADs, one per NIC; RDMA through one shared resource that exposes all 8 NICs.

## AMD versus NVIDIA

| | AMD (MI355X nodes) | NVIDIA |
| --- | --- | --- |
| Operator resource | `DeviceConfig` | `ClusterPolicy` (device plugin) or `GPUCluster` (DRA), never both |
| DRA driver name | `gpu.amd.com` | `gpu.nvidia.com`, `mig.nvidia.com`, plus `ComputeDomain` for NVLink across trays |
| Kernel driver | host RPM (DKMS), or the operator's driver install | host or driver container |
| CDI content | 3 device nodes, 2 env vars | device nodes, host driver libraries, hooks |
| RDMA stack | in-box `mlx5`, RDMA shared device plugin | Network Operator (`NicClusterPolicy`) |
