After [prefill](/learn/prefill-phase/) has filled the KV cache, **decode** produces the answer one token at a time. Each decode step runs the full model on **one new token per sequence**.

## The idea

Picture a clerk who must answer a letter one word at a time, and who works in a huge archive. For every single word they write, they must walk past **every shelf of the rulebook** (the model's weights) and reread **their own notes on this letter** (the KV cache). Only then may they write the next word.

- **The walk is the cost, not the thinking.** Deciding the word takes a moment; walking the archive takes ages. On a GPU, decode spends its time reading bytes from memory, not doing arithmetic. That is what *bandwidth-bound* means.
- **Words come strictly one after another.** Word 5 depends on word 4, so a 500-word reply needs 500 walks.
- **Batching is many clerks walking together.** If 64 clerks each need the next word of their own letter, one walk past the rulebook serves all 64. That is why servers batch users.

Where the analogy breaks: each clerk's **notes are private**, so 64 clerks still read 64 sets of notes, and the notes grow by one line per word. And in a mixture-of-experts model like gpt-oss, different clerks need **different shelves** (experts), so a bigger group walks more of the archive. Both effects show up in the numbers below.

## The latency metrics

- **Inter-token latency (ITL)**: time between two consecutive output tokens of one request, about one decode step. Also called time per output token (TPOT; vLLM exports `vllm:inter_token_latency_seconds` and `vllm:request_time_per_output_token_seconds`).
- **Output speed per user** = 1 / ITL. 20 ms ITL is 50 tokens/s.
- **End-to-end latency** $$\approx \text{TTFT} + (\text{output tokens} - 1) \times \text{ITL}$$. A 500-token answer at 20 ms ITL spends 10 s in decode alone. For long answers and reasoning models, decode dominates.
- **Throughput** = tokens per second summed over all users of a server; it sets cost per token.

## Why decode is bandwidth-bound

Per step and sequence, from the example: about 9 GFLOP against about {ex.GB(ex.step(4096).bytes)} read. That is under **2 FLOPs per byte**. An MI355X does about 5 PFLOP/s (dense FP8) but reads about 8 TB/s (spec sheet, approximate): its ridge point is about 625 FLOPs per byte ([roofline](/learn/gpu-memory-hierarchy/)). Decode sits 300× below it, so:

$$
\text{step time} \;\ge\; \frac{\text{bytes read per step}}{\text{memory bandwidth}}
$$

For one user on one MI355X that is about {ex.ms(ex.step(4096).time)}, a ceiling of about {ex.n(1 / ex.step(4096).time)} tokens/s. Real servers reach well below this (kernel launch gaps, imperfect bandwidth use, sampling, scheduling), but the ratio is what matters: the step costs bytes, not FLOPs. For a **dense** model it is worse: Llama 3.3 70B in 16-bit reads all 141 GB every step, at least 17.8 ms, so at most about 56 tokens/s per user on one MI355X, however idle its compute units are.

## Batching: sharing the weight read

If 64 users each need a decode step, the server runs them **together**: one pass over the weights, each weight matrix multiplied by a 64-row matrix instead of a single vector. The weight bytes are paid once for all 64. Two things are **not** shared:

- **KV cache**: each sequence attends over its own history, so KV bytes grow linearly with the batch.
- **Experts** (MoE): different users route to different experts, so more experts are read as the batch grows ([Mixture of experts](/learn/mixture-of-experts/#what-routing-does-to-batching)).

The pattern: **batching multiplies throughput but lowers per-user speed**. For the dense model, 64× the users costs only 1.6× the step time: batching is almost free. For MoE, batching first wakes up more experts, so per-user speed drops faster. At large batches the **KV reads** take over, and KV memory also caps how many sequences fit at all. Even at batch 256, compute use stays at a few percent of peak: on HBM GPUs decode is a bandwidth problem at every batch size people actually run.

## Continuous batching

Requests start and finish at different times. **Static batching** waits for a full batch and runs it until the longest answer ends, leaving finished slots idle. **Continuous batching** (iteration-level scheduling, from the Orca system) re-forms the batch at **every step**: finished sequences leave, new ones join after their prefill. vLLM, SGLang and TensorRT-LLM all do this. Details: [Batching and scheduling](/learn/batching-and-scheduling/).

## What makes decode faster

Decode speed per user is bounded by **$$\text{bandwidth} / \text{bytes per token}$$**. On an MI355X the weights live in HBM at about 8 TB/s, so the example step above takes at least {ex.ms(ex.steps[0].time)} ({ex.GB(ex.steps[0].bytes)} read). Every lever attacks one side of that fraction:

- **Fewer bytes per token.** Quantize weights (MXFP4 experts) and the KV cache (FP8); MoE already reads only the chosen experts.
- **More tokens per byte read.** Batch users so each weight read serves many sequences; [speculative decoding](/learn/speculative-decoding/) verifies several tokens of one user per weight read.
- **More bandwidth.** Newer HBM generations, splitting the model across GPUs so each reads only its share, or accelerators that keep weights in on-chip SRAM.
- **No interference.** Running decode on its own pool, apart from prefill, keeps long prompts from stretching decode steps ([Batching and scheduling](/learn/batching-and-scheduling/)).

<Callout tone="note" title="How this shows up when operating a server">
- User-visible output speed (ITL) depends on the decode side; TTFT depends mostly on prefill and queueing. When users report "slow", ask which one.
- A decode-heavy GPU shows high memory-bandwidth use with low compute use. That is the expected pattern, not a fault.
</Callout>

## Common misconceptions

- **"More FLOPs make decode faster."** Not below the ridge point. Bandwidth (or keeping weights on-chip) does.
- **"Batching is free throughput."** It costs per-user speed and KV memory; for MoE models it also costs extra weight reads.
- **"Decode only reads the new token."** It reads the KV of every earlier token every step, so it slows as the context grows.
- **"Tokens per second" is one number.** Per-user speed and server throughput can move in opposite directions.
