GPU tools speak in GPU indexes, PIDs and PCI addresses. Kubernetes speaks in Pods, ResourceClaims and DRA device names. In an incident you need to cross between them fast:

- "GPU 4 is throwing errors: whose Pod is that?"
- "This Pod is slow: which card is it on?"
- "The vendor wants a serial number for device <code>{t.device}</code>."

Every recipe below is read-only. The outputs are illustrative example output for an 8× MI355X node called `gpu-node-1`: realistic, but made up.

## The idea

Think of a hotel. The front desk (Kubernetes) knows guests by name and keeps a **register** of who has which room: that is the ResourceClaim. The housekeeping staff (the GPU tools) know rooms by number and see who is inside right now: that is `amd-smi process`. Every guest carries a **key card** with their name on it: that is the process's cgroup path, which contains the Pod UID.

So the join is two lookups that meet in the middle:

- *Room → guest*: who is in the room (PIDs), then read their key card (cgroup → Pod).
- *Guest → room*: look up the register (Pod → claim → device), then translate the register's room code into the number on the door (device → BDF → GPU index and slot).

Where the analogy breaks: a hotel never has two numbering systems for the same room. A GPU has five (index, BDF, card/render node, DRA device name, physical slot), and none of them is the slot number DC Ops sees on the board. Also, someone can be in a room without being in the register: a privileged Pod or a host process that opened the device directly. When the register and housekeeping disagree, believe the register for "is it allocated" and housekeeping for "is it in use".

## The identifiers and where they meet

| World | Identifier | Example on gpu-node-1 |
| --- | --- | --- |
| amd-smi / exporter | GPU index (`gpu_id`) | `4` |
| PCI | BDF | <code>{t.bdf}</code> |
| DRM | card / render node | <code>{t.card}</code>, <code>/dev/dri/{t.render}</code> |
| DRA | device name in the ResourceSlice | <code>{t.device}</code> |
| Hardware | OAM slot, board serial | slot <code>{t.oam}</code>, serial from `amd-smi static -B` |
| Linux | host PID, cgroup | <code>{t.enginePid}</code>, `/kubepods/burstable/pod<uid>/<container-id>` |
| Kubernetes | Pod, Pod UID, ResourceClaim | <code>llm-prefill-…-{t.pod.split('-').at(-1)}</code>, <code>{t.podUid.slice(0, 8)}-…</code>, <code>…-gpu-{t.claim.split('-').at(-1)}</code> |

The joins:

- **DRA device name → card and render node.** The AMD DRA driver names devices `gpu-<card>-<render>`, so <code>{t.device}</code> is <code>{t.deviceCard}</code> and <code>{t.deviceRender}</code>.
- **ResourceSlice → BDF.** Each device carries the attribute `resource.kubernetes.io/pciBusID`.
- **BDF → everything else.** `amd-smi list -e` prints index, BDF, card, render and OAM slot for each GPU.
- **PID → Pod.** The process's cgroup path contains the Pod UID and container ID.
- **Pod → GPU.** The ResourceClaim's `status.allocation` names the device, and `status.reservedFor` names the Pod UID.

## The whole node on one screen

This script prints one line per GPU: index, BDF, slot, DRA device name, PIDs, and Pod. Run it as root on the GPU node. It only reads (amd-smi, `/proc`, `crictl ps`).

```shell
#!/bin/bash
# gpumap.sh — read-only: GPU index, BDF, OAM slot, DRA device, PIDs, Pod
amd-smi list -e --json | python3 -c '
import json, sys, re, subprocess
procs = json.loads(subprocess.run(["amd-smi", "process", "--json"], capture_output=True, text=True).stdout)
pids = {g["gpu"]: [p["process_info"]["pid"] for p in g.get("process_list", [])
                   if isinstance(p, dict) and isinstance(p.get("process_info"), dict)] for g in procs}
def pod(pid):
    ids = re.findall(r"[0-9a-f]{64}", open("/proc/%d/cgroup" % pid).read())
    if not ids: return "-"
    out = subprocess.run(["crictl", "ps", "--id", ids[-1], "-o", "json"], capture_output=True, text=True).stdout
    c = json.loads(out)["containers"]
    return "%s/%s" % (c[0]["labels"]["io.kubernetes.pod.namespace"], c[0]["labels"]["io.kubernetes.pod.name"]) if c else "-"
fmt = "%-4s%-14s%-5s%-13s%-18s%s"
print(fmt % ("GPU", "BDF", "OAM", "DRA device", "PIDs", "Pod"))
for g in json.load(sys.stdin):
    ps = pids.get(g["gpu"], [])
    dev = "gpu-%s-%s" % (g["card"][4:], g["render"][7:])
    print(fmt % (g["gpu"], g["bdf"], g["oam_id"], dev, ",".join(map(str, ps)) or "-", pod(ps[0]) if ps else "-"))
'
```

<Out host="gpu-node-1" cmd="./gpumap.sh" out={t.mapOut} />

Three things to notice:

- The index order follows the BDF, not the slot: GPU 0 sits in OAM slot {t.gpus[0].oam}, GPU 2 in slot {t.gpus[2].oam}. DC Ops works in slots.
- The DRA names follow the DRM numbers, not the index: card numbers start at 1 here (`card1` is GPU 0), and on hosts where each GPU registers several DRM nodes they skip numbers. Do not guess the name from the index.
- Only two of eight GPUs are busy. That matches the two ResourceClaims allocated from this node's pool (see below).

## All GPUs in use on a node, from the claim side

```shell
kubectl get resourceclaims -A -o json | python3 -c '
import json, sys
for c in json.load(sys.stdin)["items"]:
    for r in (c.get("status", {}).get("allocation") or {}).get("devices", {}).get("results", []):
        if r["pool"] == "gpu-node-1":
            print(c["metadata"]["namespace"], c["metadata"]["name"], r["device"])'
```

On `gpu-node-1` this would print two claims: one Pod on <code>{t.device}</code> and another on <code>{t.device2}</code>. That matches the map script exactly. The **claim is the allocation ledger**. When the ledger, `amd-smi process` and the exporter disagree, believe the ledger for "is it allocated" and `amd-smi process` for "is it in use".

**Shortcut: the exporter label.** Busy GPUs carry the Pod name on their metrics (see [GPU metrics](/learn/gpu-metrics/)):

<pre class="astro-code" tabindex="0"><code>{t.exporterOut}</code></pre>

Use it for dashboards. In an incident, confirm with the claim: a blank label does not prove the GPU is free.

## NVIDIA variant

| Step | AMD | NVIDIA |
| --- | --- | --- |
| GPU → PIDs | `amd-smi process -g N` | `nvidia-smi --query-compute-apps=pid,gpu_uuid,used_memory --format=csv` |
| PID → Pod | `/proc/<pid>/cgroup`, `crictl` | the same |
| Device files | `/dev/dri/renderD*`, `/dev/kfd` | `/dev/nvidia<N>`, `/dev/nvidiactl`, `/dev/nvidia-uvm` |
| Device ↔ BDF | `amd-smi list -e` | `nvidia-smi --query-gpu=index,uuid,pci.bus_id --format=csv` |
| Claim → device | ResourceClaim `status.allocation` | the same (NVIDIA DRA driver `gpu.nvidia.com`; not verified here) |

## Logs around a GPU Pod

| Want | Command |
| --- | --- |
| Prefill engine log | `kubectl -n gpu-demo logs <pod> -c prefill` (add `--previous` after a crash) |
| Why it restarted | `kubectl -n <ns> describe pod <pod>`: last state, exit code (139 = segfault, for example when the GPU dies) |
| The node's view | `journalctl -k --since -1h \| grep -i amdgpu` on the GPU node |
| DRA driver | `kubectl -n kube-amd-gpu logs <default-dra-driver-pod-on-node>` |
| Exporter | `kubectl -n kube-amd-gpu logs <default-metrics-exporter-pod-on-node>` |
