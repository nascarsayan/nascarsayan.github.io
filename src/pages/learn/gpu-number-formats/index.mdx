A model is billions of numbers (its **weights**). How many bits each number takes decides three things at once: how much GPU memory the model needs, how many bytes each generated token must read from memory, and how fast the matrix engines run. Datacenter GPUs now compute on numbers as small as **4 bits**. This page shows what those formats are, encodes real values in them, and shows what they cost in accuracy.

## The idea first

**A float is scientific notation with a fixed number of digits.** Write 0.3 as $$1.2 \times 2^{-2}$$. A floating-point number stores exactly those pieces, in binary, in a fixed number of bits:

| Field | The question it answers | In $$0.3 = 1.2 \times 2^{-2}$$ | What more bits buy |
| --- | --- | --- | --- |
| **sign** | positive or negative? | + | (always 1 bit) |
| **exponent** | roughly how big: which power of two? | $$2^{-2}$$ | a wider **range**: bigger and smaller numbers |
| **mantissa** | where exactly between that power of two and the next? | 1.2 | finer **precision**: more digits |

A format is named by how it splits its bits: `E4M3` is 4 exponent bits and 3 mantissa bits, plus the sign, 8 bits in total.

**A float is a ruler whose ticks spread out as numbers grow.** With 3 mantissa bits, every power-of-two interval (1 to 2, 2 to 4, 4 to 8 …) gets the same **8 ticks**. So between 1 and 2 the step is 0.125; between 8 and 16 it is 1. Every value you store snaps to the nearest tick. These are all the values FP8 E4M3 can hold between 0 and 16:

**Scaling is choosing the unit.** A 4-bit float holds only 0, 0.5, 1, 1.5, 2, 3, 4 and 6 (and their negatives). A real weight such as 0.0137 is far below all of them. The fix is the one you use when you write a length in millimetres instead of metres: store the small numbers in a **unit** (a *scale factor*) that fits the data, and write the unit down once next to them. $$\text{Real value} = \text{stored number} \times \text{scale}$$.

**Where the analogy breaks.** The unit is not chosen per number: one scale is shared by a **block** of neighbouring weights (32 in the OCP MX formats), and in MX it must be a power of two. If one weight in the block is much bigger than the rest, the unit has to fit that one, and the small ones lose their digits. The second worked example below shows exactly that.

## The formats

| Format | Bits | Layout | Range and precision, roughly | Typical use |
| --- | --- | --- | --- | --- |
| FP32 | 32 | E8M23 | huge range, about 7 decimal digits | accumulators, optimizer state |
| BF16 | 16 | E8M7 | FP32's range, about 2–3 digits | training, most served weights today |
| FP16 | 16 | E5M10 | small range (max 65,504), more digits | older training, some inference |
| FP8 E4M3 | 8 | E4M3 | max ±448 | inference weights and activations |
| FP8 E5M2 | 8 | E5M2 | max ±57,344, fewer digits | gradients in training |
| FP6 | 6 | E2M3 or E3M2 | max 7.5 or 28 | weights, with block scales |
| FP4 | 4 | E2M1 | only 0, ±0.5, ±1, ±1.5, ±2, ±3, ±4, ±6 | weights, with block scales |

BF16 keeps FP32's 8 exponent bits and drops mantissa bits: same range, fewer digits. FP16 makes the opposite trade. FP4 has exactly 16 bit patterns.

## Scaling: one shared multiplier per block

- **Per-tensor scaling** (classic FP8): one scale for the whole tensor. One outlier anywhere forces a large scale, and the small values lose their digits.
- **Block scaling** (microscaling): one scale per small **block** of neighbouring values. An outlier only hurts its own block.

The industry standard for block scaling is the **OCP Microscaling (MX)** specification, written by AMD, Arm, Intel, Meta, Microsoft, NVIDIA, Qualcomm and others. In every concrete MX format a block is **32 elements** and the shared scale is **E8M0**: an 8-bit power of two, with no mantissa.

| MX format | Element | Bits per value including the scale |
| --- | --- | --- |
| MXFP8 | E4M3 or E5M2 | 8 + 8/32 = 8.25 |
| MXFP6 | E2M3 or E3M2 | 6.25 |
| MXFP4 | E2M1 | 4.25 |
| MXINT8 | 8-bit integer | 8.25 |

NVIDIA's own 4-bit format, **NVFP4**, uses two levels of scale: an FP8 (E4M3) scale for every **16** values, plus one FP32 scale for the whole tensor. The smaller block and the finer scale (E4M3 has mantissa bits; E8M0 does not) cost a little more space, about 4.5 bits per value, and NVIDIA states the accuracy is close to FP8. AMD CDNA 4 (MI350 series) supports the OCP MX formats in hardware. NVIDIA documents NVFP4 as the Blackwell 4-bit format; this page did not verify which OCP MX formats Blackwell runs natively.

## Why fewer bits are faster

Two separate effects:

1. **Memory and bandwidth.** Half the bits means half the bytes to store and half the bytes to read per token. Decode (generating one token at a time) reads every weight once per step, so it gets faster almost in proportion. See [memory and roofline](/learn/gpu-memory-hierarchy/).
2. **Math throughput.** A matrix engine has fixed wires. Narrower numbers let it do more multiply-adds per clock. AMD's CDNA 4 white paper lists the rate per CU per clock; times 256 CUs and 2.4 GHz that gives the spec-sheet peaks:

FP32 matrix math runs at 157.3 TFLOPS and FP64 at 78.6 TFLOPS: a GPU built for AI gives up wide-number speed. MI355X runs MXFP6 at the MXFP4 rate. NVIDIA states 15 PFLOPS dense NVFP4 and 5 PFLOPS dense FP8 for one Blackwell Ultra GPU (the GPU in GB300); it lists FP6 support for Blackwell Ultra Tensor Cores, but this page did not verify its rate. All of these are vendor peaks: real kernels reach a fraction.

"Sparsity" numbers on spec sheets are double the dense ones. They apply only when a tensor follows a 2:4 pattern (two of every four values are zero). LLM weights normally do not, so use the dense figures.

## How big is the model?

A 70-billion-parameter dense model is 140 GB in BF16, 70 GB in FP8 and about 37 GB in MXFP4. Reading it once at 8 TB/s takes at least 17.5, 8.8 and 4.6 ms. Halving the bits halves the floor on time per token, and the memory freed goes to the [KV cache](/learn/attention-and-kv-cache/), which decides how many requests fit at once. Try other sizes:

## Where the format lives in the stack

- The **checkpoint** (model files) is stored in some format, for example BF16 or a pre-quantized FP8 or MXFP4 release.
- The **serving engine** (vLLM) chooses kernels for that format. A flag or the model's config picks the quantization method.
- The **kernels** use matrix-core instructions for that format: MFMA (matrix fused multiply-add) on AMD, Tensor Core MMA on NVIDIA. See [PTX and AMDGCN ISA](/learn/gpu-isa-ptx/).
- **Accumulation** happens in wider precision (FP32), so only the inputs are narrow.

If a GPU lacks native support for a format, software can still unpack it to a wider type before the math. That saves memory but not math time. MI300X (CDNA 3), for example, has FP8 but no FP4 or FP6 matrix support; MI355X (CDNA 4) adds them.

<Callout tone="note" title="How this shows up in operations">

- **Memory per Pod** depends on the format. An inference server Pod often holds most of an MI355X's 288 GB; most of that is the serving engine pre-reserving memory for KV cache, not weights alone.
- **The same image can behave differently** on MI300X and MI355X if the model uses FP4: one has hardware for it, one does not.
- **A model change can be a hardware-fit change.** Moving a model from FP8 to BF16 doubles weight memory; it may stop fitting on the planned number of GPUs.
- **Metrics do not show the format.** `amd-smi` and `nvidia-smi` report memory used and activity, not which number format the kernels use. Ask the inference team or read the serving config.

</Callout>

## Common misconceptions

- "**FP4 is 4× faster than FP16 everywhere.**" Only the matrix math is. Attention, normalization and communication do not speed up the same way.
- "**MXFP4 and NVFP4 are the same.**" Both are 4-bit E2M1 elements, but the block size (32 vs 16) and scale type (E8M0 vs E4M3) differ. A checkpoint is quantized for one of them.
- "**FP8 is one format.**" There are two (E4M3, E5M2), and older non-OCP variants also exist. The OCP names are the standard ones.
- "**Peak PFLOPS tell you the speed.**" Decode is limited by memory bandwidth, so HBM TB/s usually matters more than PFLOPS for it.
