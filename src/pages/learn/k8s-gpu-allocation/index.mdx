## The idea

Kubernetes has no built-in idea of a GPU. A GPU is a PCIe card with a kernel driver (`amdgpu` for AMD Instinct) and a few character device files under `/dev`. A container can use one only if those files exist inside the container and no other container is using that card. So something has to answer four questions: **what GPUs exist, what does this Pod need, which GPU does it get, and how do the device files get into its container?**

Think of a theatre with reserved seats:

- The **seat map** lists every seat with its row and its view. In Kubernetes this is the **ResourceSlice**: each node's DRA driver lists its 8 GPUs by name, with attributes such as NUMA node and PCI address.
- A **booking** says "one seat, stalls". This is the **ResourceClaim**: "one device of class `gpu.amd.com`".
- The **box office** picks a free seat that matches, and prints it on the ticket *before* you travel. This is the **scheduler**: it writes "`gpu-5-132` on `gpu-node-1`" into the claim's status, then binds the Pod to that node.
- The **usher** walks you to that exact seat. This is the **kubelet** with the **DRA driver**: they turn the claim into device files in the container, through a small file format called [CDI](/learn/cdi-device-injection/).

<Diagram spec={idea} title="Four questions, four pieces" mode="build">
  <Step focus="inv">What exists? The driver publishes the seat map: one ResourceSlice per node, one entry per GPU.</Step>
  <Step focus="req">What do I need? Each Pod gets a booking: a ResourceClaim for one GPU.</Step>
  <Step focus="pick, inv -> pick, req -> pick">Which one, and where? The scheduler matches bookings to free seats and writes the answer into the claim.</Step>
  <Step focus="hand, pick -> hand">How do I get it? On the chosen node, the kubelet and the driver put that GPU's device files into the container.</Step>
</Diagram>

Where the analogy breaks: a Pod does not book its own ticket. A **template** in the Deployment stamps out one claim per Pod, and the claim dies with the Pod. Several containers can sit in the same "seat" by naming the same claim. And the seat map says nothing about whether a seat is broken: a dead GPU stays listed unless something removes or taints it.

The older model, the **device plugin**, is a car park with a sign "8 spaces free". The scheduler only sees the number. The attendant at the gate (the kubelet on the node) picks a space when you arrive, and nobody upstairs knows which one you got. The sample cluster on this page uses the theatre (DRA) for GPUs, and still uses the car park for RDMA NICs.

When the Pod is deleted the path runs backwards: the kubelet calls `NodeUnprepareResources` (the driver deletes the CDI file), the resourceclaim controller removes the Pod from `reservedFor`, and then deletes the claim. <code>{c.device}</code> is free again, and the replacement Pod gets a new claim, possibly for another GPU on another node.

## Model 1: device plugins

The **device plugin API** is the older model: beta in Kubernetes 1.10, GA in 1.26, gRPC API version `v1beta1`. It treats devices like CPU or memory: a node has $$N$$ units of an **extended resource**, and Pods ask for a count.

### How it works, step by step

<Diagram spec={plugin} title="Device plugin: a count goes up, the kubelet picks the device" autoSteps />

- **Register and advertise.** The plugin opens its own gRPC socket under `/var/lib/kubelet/device-plugins/`, calls `Register` on `kubelet.sock` in the same directory, then streams device IDs with a `Healthy`/`Unhealthy` flag over `ListAndWatch`. The kubelet publishes the healthy count in `status.allocatable`.
- **Schedule by count.** A Pod sets `resources.limits: {amd.com/gpu: 1}` (whole integers, no overcommit). The scheduler finds a node where `allocatable − already requested ≥ 1`. It does **not** pick a device.
- **Allocate on the node.** At admission the kubelet's device manager picks free IDs (optionally asking `GetPreferredAllocation` for a topology-friendly set) and calls `Allocate`. The answer is device nodes, mounts, env vars, annotations or CDI names.
- **Record locally.** The choice lives only in `kubelet_internal_checkpoint`. Tools ask the kubelet's **PodResources API** (`List`, `GetAllocatableResources`) over a local socket.

The plugin must register again when the kubelet restarts (the socket is recreated). An unhealthy device lowers allocatable; running Pods are not touched.

### The same API for RDMA NICs

A cluster that uses DRA for GPUs often still runs a device plugin on every GPU node, for RDMA NICs. The files on `gpu-node-1`:

```text
/var/lib/kubelet/device-plugins/
  kubelet.sock                   # kubelet registration endpoint
  hca_devices.sock               # the RDMA shared device plugin
  kubelet_internal_checkpoint    # which Pod got which device IDs
```

The node advertises `rdma/hca_devices: 1k` in `status.allocatable`, and each prefill container asks for `rdma/hca_devices: "1"`. That is the device plugin model in action. See [GPU Pod networking](/learn/gpu-pod-networking/).

### Limits of a count

- **No properties.** `amd.com/gpu: 1` cannot say "with at least 192 GiB of memory" or "on the same PCIe root as NIC 3". Node labels are a workaround, but they describe the whole node, not one GPU.
- **The scheduler is blind.** It knows how many GPUs a node has free, not which ones. Topology choices happen late, on the node, after placement.
- **No cluster-wide record.** Which Pod has which GPU is local kubelet state. Fault handling ("which Pod uses the GPU at PCI `0000:8b:00.0`?") needs a per-node query.
- **Partitions are awkward.** A partitioned MI355X (for example CPX mode, several logical GPUs per card) needs another resource name or a different count per node. See [GPU partitioning](/learn/gpu-partitioning/).
- **No sharing model.** Time-slicing tricks advertise one GPU as several fake IDs.

## Model 2: Dynamic Resource Allocation

**DRA** is the API group `resource.k8s.io`. Version `v1` is **stable since Kubernetes 1.34** and on by default. A 1.35 cluster serves only `resource.k8s.io/v1`:

```shell
$ kubectl api-resources --api-group=resource.k8s.io
NAME                     APIVERSION           NAMESPACED   KIND
deviceclasses            resource.k8s.io/v1   false        DeviceClass
resourceclaims           resource.k8s.io/v1   true         ResourceClaim
resourceclaimtemplates   resource.k8s.io/v1   true         ResourceClaimTemplate
resourceslices           resource.k8s.io/v1   false        ResourceSlice
```

DRA borrows the shape of storage: a **DeviceClass** is like a StorageClass, a **ResourceClaim** is like a PersistentVolumeClaim, and a **ResourceSlice** is the inventory a driver publishes. The difference from storage is that the scheduler itself does the matching; there is no external provisioner.

  <Step path="tmpl => claim" title="Stamp">The resourceclaim controller creates one claim per Pod from the template.</Step>
  <Step focus="pod, pod -> claim" title="Reference">The Pod lists the claim in spec.resourceClaims; the container names it in resources.claims.</Step>
  <Step path="sched => claim" focus="slice, class, sched -> slice, sched -> class" title="Allocate">The scheduler reads slices and the class, then writes the chosen device into the claim's status.</Step>
</Diagram>

### How it works, in one line per step

The worked example above shows each step with example objects. In short: the driver **publishes** a ResourceSlice per node; a DeviceClass **classifies** devices with CEL; the resourceclaim controller **stamps** a claim per Pod from the template; the scheduler **allocates** (it holds the device in memory in `Reserve` so two Pods in flight cannot take the same GPU, then writes `status.allocation` and `reservedFor` in `PreBind`, then binds); the kubelet has the driver **prepare** it (CDI); on Pod exit the kubelet **unprepares** and the claim is **released** and deleted. Details: [DRA objects in detail](/learn/dra-objects/), [DRA on the node](/learn/dra-on-the-node/), [CDI](/learn/cdi-device-injection/).

## Side by side

| | Device plugin | DRA |
| --- | --- | --- |
| Pod asks for | `resources.limits: {amd.com/gpu: 1}` | `spec.resourceClaims` → claim for 1 device of class `gpu.amd.com` |
| Capacity lives in | Node `status.allocatable` | `ResourceSlice` objects; nothing on the Node |
| Unit | integer count | named device with attributes and capacities |
| Who picks the device | kubelet, after scheduling | scheduler, before binding |
| Record of the choice | kubelet checkpoint file on the node | `ResourceClaim.status.allocation` in the API |
| Device-level selection | none (node labels only) | CEL on attributes; constraints across devices |
| Several containers or Pods share one device | no | yes, by referencing the same claim |
| Node agent API | `Register`, `ListAndWatch`, `Allocate`, `GetPreferredAllocation`, `PreStartContainer` | registration, `NodePrepareResources`, `NodeUnprepareResources` |
| How devices enter the container | `Allocate` response (device nodes, mounts, env, or CDI names) | CDI device IDs |
| GA in | 1.26 | 1.34 |

<Callout tone="warn" title="Never both for the same GPUs">
A device plugin and a DRA driver do not know about each other. If both advertise the same 8 GPUs, the scheduler can give GPU 3 to one Pod through `amd.com/gpu` and to another through a claim. The AMD operator rejects a `DeviceConfig` with both enabled, but only at reconcile time; `kubectl apply` still succeeds.
</Callout>

## A typical DRA-only setup

- **DRA only.** The AMD device plugin is off in the operator's `DeviceConfig` (`devicePlugin.enableDevicePlugin: false`) and the DRA driver is on (`draDriver.enable: true`). See [GPU operators](/learn/gpu-operators/).
- **Whole GPUs, exclusive.** GPUs run in SPX/NPS1 mode, so each card is one device. No partitions, no sharing. A request that cannot be met stays Pending.
- **One claim per Pod.** Deployments use a `ResourceClaimTemplate` with `allocationMode: ExactCount`, `count: 1`. Up to 8 replicas share an MI355X node, one per GPU. Nothing spreads them across nodes unless you add topology spread constraints or anti-affinity; without them, one node failure can take out many replicas at once.
- **Placement.** A Pod that requires only a GPU-node label plus a claim can land on any GPU node. Restricting a namespace to its own nodes takes extra affinity or an admission policy.
- **The driver is part of the platform.** The DRA driver is a DaemonSet the cluster operator deploys and upgrades. If it is down on a node, no new GPU Pod can start there; running Pods keep their GPUs. A readiness gate can check that it is registered before the node takes GPU work.
- **Allocated is not ready.** A claim in state `allocated,reserved` says the GPU is assigned, not that the workload is up. The application's readiness probe owns that.

## Misconceptions

- **"No `amd.com/gpu` on the node means the GPUs are missing."** No. Under DRA, capacity is only in ResourceSlices. Check `kubectl get resourceslices --field-selector spec.nodeName=<node>`.
- **"DRA is alpha."** The core API is GA since 1.34. Some *features* on top (device taints, partitionable devices, consumable capacity) are still alpha in 1.35. See [DRA objects in detail](/learn/dra-objects/#feature-gates-in-kubernetes-135).
- **"The claim belongs to the Deployment."** A template-generated claim is owned by one Pod. When the Pod is deleted, its claim goes too, and a replacement Pod gets a new claim, possibly for a different GPU on a different node.
- **"DRA gives the scheduler GPU health."** Not by itself. A dead GPU stays in the ResourceSlice unless the driver removes it or something taints it.

## NVIDIA

NVIDIA has both models too. The **NVIDIA device plugin** advertises `nvidia.com/gpu` and is managed by the GPU Operator's `ClusterPolicy`. The **NVIDIA DRA driver** publishes devices of driver `gpu.nvidia.com` (plus `mig.nvidia.com` for MIG slices) and adds the `ComputeDomain` API for multi-node NVLink. In current operator releases it is managed by a separate `GPUCluster` resource, and a cluster has either a `ClusterPolicy` or a `GPUCluster`, not both. See [GPU operators](/learn/gpu-operators/) and [rack-scale GPUs](/learn/rack-scale-gpus/).
