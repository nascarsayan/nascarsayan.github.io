A CPU core runs one thread fast and guesses ahead to avoid waiting. A GPU does the opposite. It runs tens of thousands of slow threads, and when one group must wait for memory it runs another group. This page explains how that works, from one line of kernel code down to the hardware unit that runs it. The main example is the AMD MI355X in an 8-GPU MI355X server, with NVIDIA beside it.

## The idea first

Picture a factory floor with thousands of workbenches. The work order says "do the same job on a million parts". Nobody plans who does which part: each worker reads a number off their badge and takes that part.

| Piece | Everyday picture | The question it answers |
| --- | --- | --- |
| **Thread** | one worker, with their own bench (registers) | "Which part is mine?" (its index `i`) |
| **Wavefront** (AMD, 64 threads) / **warp** (NVIDIA, 32) | a squad that follows **one foreman's commands** in lockstep: "everyone, pick up your part; everyone, add" | "What does the squad do next?" (one instruction for all) |
| **EXEC mask** | the foreman's list of who takes part in this command; the rest stand still | "Who acts on this instruction?" |
| **Block / workgroup** | a few squads given the same room, with a shared shelf (LDS) | "Who can share data and wait for each other?" |
| **CU / SM** | a room with 4 foremen's stations (SIMDs) | "Where does a block run?" |
| **Occupancy** | how many squads fit in the room at once, limited by benches (registers) and shelf space (LDS) | "How many squads are ready to step in?" |

**Why so many squads?** Parts come from a far warehouse (HBM). A trip takes hundreds of cycles. When one squad waits for a delivery, its foreman's station points at another squad that already has its parts. Nobody leaves their bench, so the switch is free. That is **latency hiding**, and it only works if enough squads are in the room.

**Where the picture breaks.** A squad cannot split up: if the command is "those with a red part, paint it", everyone else stands idle until it is done, then the squad does the other branch. And the "workers" are not little CPUs: they have no instruction stream of their own; only the foreman (one per wave) reads the recipe.

## A kernel is one function launched many times

A **kernel** is a function that runs on the GPU. You launch it once, and the GPU runs one copy per **thread**. Each copy reads a few built-in IDs to find out which piece of data it owns.

```cpp
// Real CUDA/HIP source (compiles unchanged with nvcc and hipcc). y = a*x + y.
__global__ void axpy(float a, const float* x, float* y, int n) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;   // which element am I?
  if (i < n) y[i] = a * x[i] + y[i];
}
axpy<<<(n + 255) / 256, 256>>>(2.0f, x, y, n);      // grid of blocks, 256 threads each
```

The launch says: make a **grid** of blocks, and give each **block** 256 threads. For `n` = 1,000,000 that is 3,907 blocks and about a million threads. The programmer never says which core runs what. The hardware decides.

## The four levels

| Level | NVIDIA (CUDA) | AMD (HIP) | Runs on | Shares |
| --- | --- | --- | --- | --- |
| One copy of the function | thread | work-item (thread) | one lane of a vector unit | nothing; own registers |
| Lockstep group | **warp**, 32 threads | **wavefront**, 64 threads on CDNA | one scheduler / one SIMD | one instruction stream, one program counter |
| Cooperating group | thread block (CTA) | workgroup | one SM / one CU, never split | shared memory (NVIDIA) / LDS (AMD), barriers |
| Whole launch | grid | grid | the whole GPU | HBM (global memory) |

Words used below:

- **CU (Compute Unit)** is AMD's compute block. **SM (Streaming Multiprocessor)** is NVIDIA's. They play the same role.
- **SIMD (Single Instruction, Multiple Data)** is one vector unit inside a CU. An MI355X CU has 4. (AMD uses "SIMD" as the name of this hardware block; the programming model on top is SIMT. See [SIMD vs SIMT](#simd-vs-simt).)
- **LDS (Local Data Share)** is AMD's on-chip scratch memory, shared by one workgroup. NVIDIA calls it **shared memory**.
- **HBM (High Bandwidth Memory)** is the GPU's main memory: 288 GB on an MI355X.

An 8-GPU node shows 8 such agents, one per GPU. How to read it:

- 256 CUs × 4 SIMDs = **1,024 SIMDs** per GPU.
- Each SIMD holds up to 8 wavefronts at once (32 per CU ÷ 4 SIMDs). The whole GPU can have 8,192 wavefronts, or 524,288 threads, **resident** at the same moment.
- A workgroup has at most 1,024 threads (16 wavefronts). The `GROUP` segment is the LDS: up to 160 KB per workgroup.
- The 4 MB L2 is **per XCD**. An MI355X has 8 XCDs (compute dies) of 32 CUs each, so 32 MB of L2 in total. The 256 MB "L3" is AMD Infinity Cache, shared by the whole GPU (ROCm hardware spec table).

The NVIDIA equivalents, from the CUDA programming guide for compute capability 9.0 (H100) and 10.0 (B200): 64 resident warps per SM (2,048 threads), 32 resident blocks per SM, 64K 32-bit registers per SM, at most 255 registers per thread, up to 228 KB of shared memory per SM (227 KB per block). An H100 SXM has 132 SMs.

## Lockstep: SIMT and the execution mask

NVIDIA calls the model **SIMT (Single Instruction, Multiple Threads)**. You write code for one thread. The hardware groups 32 (NVIDIA) or 64 (AMD CDNA) threads and fetches **one instruction for the whole group**. Each thread applies it to its own registers.

### SIMD vs SIMT

| | SIMD (Single Instruction, Multiple Data) | SIMT (Single Instruction, Multiple Threads) |
| --- | --- | --- |
| What it names | the hardware: one instruction drives many lanes at once | the programming model: you write one scalar thread; hardware runs 32 or 64 of them on those lanes |
| Who sees the width | the programmer, in every instruction (CPU AVX-512: 16 floats per `vaddps`) | mostly nobody: code is written per thread; width shows up only in warp/wave intrinsics and divergence cost |
| Branches | you mask by hand (blend / mask registers) | the hardware masks for you (`EXEC` on AMD, active mask on NVIDIA) and runs both sides of a split branch |
| Memory access | one vector load of contiguous data | each thread has its own address; the hardware merges neighbouring addresses (coalescing) |
| Per-lane state | lanes share one program counter, no per-lane identity | each thread has its own registers and index (`threadIdx`); since NVIDIA Volta each thread also has its own program counter, so threads of one warp can diverge and reconverge more freely |

So a GPU is **SIMT software on SIMD hardware**. AMD's block names say so: a CU contains four "SIMDs", and the wavefronts that run on them are SIMT thread groups. NVIDIA coined "SIMT" and avoids "SIMD" for its own units. When a page says "the SIMD", it means AMD's hardware unit; "SIMT", "lockstep" and "divergence" are about how threads execute on it.

### How a wave runs on one SIMD

On a CDNA CU each SIMD has 16 lanes. A wave64 vector instruction therefore takes 4 cycles, 16 threads per cycle. With 4 SIMDs, the CU can start one vector instruction on each SIMD every cycle, if enough wavefronts are ready (AMD HIP hardware-implementation guide).

What happens to `if (i < n)` when only some threads pass? The group cannot split. Instead the hardware keeps an **execution mask**: one bit per thread. Instructions still run for the whole group, but threads whose bit is 0 do not write results. On AMD the mask is a real 64-bit register named `EXEC`, and you can see it in compiled code. This is illustrative `gfx950` assembly of the kind `hipcc --offload-arch=gfx950 -O3 --save-temps` produces for the `axpy` kernel above (example ROCm 7.0.0):

```amdgcn
; example compiler output, gfx950 (MI355X), trimmed; comments added
  v_add_u32_e32        v0, s2, v0           ; i = blockIdx.x*blockDim.x + threadIdx.x  (v = per lane)
  v_cmp_gt_i32_e32     vcc, s4, v0          ; vcc = one bit per lane: n > i ?
  s_and_saveexec_b64   s[2:3], vcc          ; EXEC &= vcc  (lanes with i >= n switch off)
  s_cbranch_execz      .LBB0_2              ; if no lane is left, skip the body
  global_load_dword    v4, v[2:3], off      ; x[i]
  global_load_dword    v5, v[0:1], off      ; y[i]
  s_waitcnt            vmcnt(0)             ; wait for both loads
  v_fmac_f32_e32       v5, s2, v4           ; y += a * x
  global_store_dword   v[0:1], v5, off
.LBB0_2:
  s_endpgm
```

Two kinds of registers appear:

- `v` registers (**VGPRs**, vector general-purpose registers) hold one 32-bit value **per lane**: 64 values for a wave64.
- `s` registers (**SGPRs**, scalar registers) hold one value **for the whole wavefront**. The compiler puts anything that is the same for every thread there: `a`, `n`, the array base addresses, `blockIdx.x`. A separate scalar unit runs the `s_*` instructions.

NVIDIA has the same ideas under other names. Its machine code (SASS) uses **predicates**: `ISETP.GE.AND P0, PT, R7, UR4, PT` then `@P0 EXIT`. `UR` registers are NVIDIA's "uniform" (per-warp) registers.

### Divergence: one wave through an if/else, step by step

**Divergence** means threads of one wave want different paths. The wave cannot split, so the hardware runs both paths one after the other and flips `EXEC` between them. Follow one wave through this kernel:

```cpp
__global__ void branchy(const float* x, const float* a, const float* b, float* y, int n) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n) {
    float v = x[i];
    if (v > 0.0f) y[i] = a[i] * v;    // "then" side
    else          y[i] = b[i] - v;    // "else" side
  }
}
```

The instructions in each step are illustrative `gfx950` compiler output (`hipcc --offload-arch=gfx950 -O3 --save-temps`, example ROCm 7.0.0), trimmed. The data is made up: one workgroup of 64 threads (one wave), **n = {ex.n}**, a[i] = {ex.A}, b[i] = {ex.B}, and a mix of positive and negative x. Every mask and value below is computed from those inputs. Each row of the grid is what the 16-lane SIMD does in one cycle; a wave64 instruction takes 4 cycles.

## Scheduling and latency hiding

A load from HBM takes hundreds of nanoseconds. At 2.4 GHz that is hundreds to over a thousand clock cycles. Vendors do not publish exact figures, so treat this as an order of magnitude. The GPU does not try to make the wait shorter. It fills the wait with other work:

<Diagram spec={hide} autoSteps title="One SIMD, two resident wavefronts" caption="Instruction names from the gfx950 ISA. Real kernels keep several loads in flight per wave, and up to 8 waves per SIMD." />

Each cycle, the scheduler for a SIMD (NVIDIA: each of the SM's four warp schedulers) picks a resident wave whose next instruction has its inputs ready, and issues it. Switching costs nothing, because every resident wave keeps its registers in the register file the whole time. Nothing is saved or restored. That is the key difference from CPU threads.

AMD code shows the waits as instructions. `s_waitcnt vmcnt(N)` means "stall this wave until at most N vector-memory loads are outstanding". `lgkmcnt` counts LDS, scalar-memory and other short operations. NVIDIA encodes waits as scoreboard bits inside each SASS instruction, so you do not see separate wait instructions.

### How many waves do you need?

**Little's law**: $$\text{data in flight} = \text{bandwidth} \times \text{latency}$$. A worked example with round numbers (the latency is assumed, not measured):

| Step | Value |
| --- | --- |
| MI355X HBM bandwidth (spec, approximate) | 8 TB/s |
| Assumed load latency | 500 ns |
| Bytes in flight to keep HBM busy | $$8 \times 10^{12} \times 500 \times 10^{-9}$$ = **4 MB** |
| Per CU (÷ 256) | about **16 KB** |
| One `global_load_dwordx4` per wave (64 lanes × 16 B) | 1 KB |
| Waves per CU needed, one load each | about **16** (half of the 32 slots) |

A memory-bound kernel therefore needs either many resident waves, or fewer waves that each keep several independent loads in flight (**instruction-level parallelism**). Both work. Fast GEMM kernels often run at low occupancy and use the second approach.

## Occupancy: how many waves fit

**The idea.** Every resident wave keeps its registers on the chip the whole time; that is why switching is free. So the register file, the LDS and the wave slots are a fixed room, and each workgroup takes a share of all three. **Occupancy** $$= \text{resident waves} / \text{the maximum}$$ (8 per SIMD on AMD, 64 warps per SM on NVIDIA). Whichever resource runs out first sets it. A kernel that needs more registers per thread holds fewer waves, and so has fewer waves to switch to while one waits.

The resources on MI355X (CDNA4, gfx950):

| Resource | Size | Source |
| --- | --- | --- |
| Wave slots | 8 per SIMD, 32 per CU | `rocminfo` above |
| Vector register file | 512 KB per CU = 128 KB per SIMD → 128 KB ÷ (64 lanes × 4 B) = **512 VGPRs per lane** | ROCm GPU hardware specs |
| Per-wave registers | up to 256 `v` + 256 `a` (AGPRs, accumulation registers for matrix cores); counted as align(v, 4) + a, in blocks of 8 | CDNA4 ISA guide §3.6.4, LLVM AMDGPU docs |
| LDS | 160 KB per CU, allocated in 1,280-byte granules (MI300X: 64 KB, 512-byte granules) | `rocminfo`, LLVM AMDGPU docs |

On H100 (compute capability 9.0): 64K 32-bit registers per SM, split over 4 sub-partitions and allocated per warp in units of 256; up to 228 KB shared memory per SM, plus 1 KB that CUDA reserves per block; 64 warp slots and 32 block slots (CUDA programming guide; algorithm from `cuda_occupancy.h` in the CUDA toolkit).

## How the hardware places work

1. The host writes a **dispatch packet** (kernel address, grid and block size, argument pointer) into a queue in memory. On AMD these are HSA AQL queues; `rocminfo` shows up to 128 queues per GPU.
2. The GPU's command processor reads the packet and hands workgroups to CUs that have room.
3. A workgroup stays on one CU until it finishes. Its waves are spread over the CU's 4 SIMDs.
4. When a workgroup ends, its registers and LDS are freed and the next workgroup starts there.

On MI300- and MI355-class GPUs the XCDs are separate dies. In SPX mode (the whole GPU as one device), workgroups are handed to the 8 XCDs **round-robin**, and each XCD has its own 4 MB L2. Neighbouring workgroups therefore do not share an L2. Tuned kernels remap workgroup IDs so tiles that reuse the same data land on the same XCD (ROCm workload optimization guide). → [Memory hierarchy](/learn/gpu-memory-hierarchy/)

## Common misconceptions

- **"A CUDA core is a core."** It is one lane of a vector unit, with no program counter of its own. The closest thing to a CPU core is one SIMD (AMD) or one SM sub-partition (NVIDIA).
- **"More threads per block is faster."** A block only needs to be a multiple of the warp/wave size and large enough to fill the CU. 256 is a common default on both vendors.
- **"100 % occupancy is the goal."** Occupancy only needs to be high enough to hide latency. Many of the fastest LLM kernels run 1–2 waves per SIMD.
- **"Threads in a warp are independent."** They share one instruction stream. Since Volta, NVIDIA lets diverged threads interleave (independent thread scheduling), but they still execute in groups. Code that relies on implicit warp synchronization is a classic porting bug.

## How this shows up in operations

- **Same model, different GPU, different speed.** Kernels are tuned for one CU shape. A kernel tuned for MI300X (64 KB LDS, 304 CUs) is not tuned for MI355X (160 KB, 256 CUs). → [PTX and AMDGCN](/learn/gpu-isa-ptx/) explains why binaries are built per chip.
- **A busy GPU is not necessarily doing math.** Utilization counters such as `amd-smi metric` GFX activity say the compute engine had work, not that the matrix cores were busy. A memory-bound kernel can look fully busy. → [GPU metrics](/learn/gpu-metrics/)
- **A hung kernel is a wave that never retires.** `amdgpu` ring timeouts in `dmesg` mean queued work stopped making progress. → [GPU failures](/learn/gpu-failures/)

## Why this matters above

- Matrix multiplies split into tiles; each workgroup computes one tile with matrix-core instructions. → [PTX and AMDGCN](/learn/gpu-isa-ptx/), [GEMM tiling](/learn/gemm-tiling/)
- Whether a kernel waits on math or on memory decides which hardware suits it. → [Memory hierarchy and roofline](/learn/gpu-memory-hierarchy/)
